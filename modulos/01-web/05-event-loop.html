El event loop y el frame

JavaScript tiene un solo hilo, y lo comparte con el cálculo de estilos, el layout y el pintado. Entender en qué orden se ejecutan las tareas, las microtareas y los callbacks de requestAnimationFrame, y cuándo pinta el navegador, es entender por qué una animación va fluida, tiembla o se congela.

⏱ 90 minRequisitos: 1.3, 1.4

Al terminar esta lección

  • Sabrás qué es la pila de llamadas, la cola de tareas y la de microtareas, y exactamente cuándo se vacía cada una.
  • Conocerás los pasos de un frame (callbacks de rAF, estilo, layout, pintado, composición) y cuándo ocurren.
  • Resolverás puzzles de orden con setTimeout, promesas, queueMicrotask y requestAnimationFrame, y sabrás cuáles no tienen respuesta única.
  • Entenderás por qué una tarea larga congela una animación de JavaScript pero no una de CSS sobre transform, y cómo trocear el trabajo.
  • Conocerás las rarezas de los temporizadores, los relojes (performance.now() frente a Date.now()) y las pestañas en segundo plano.
  • Detectarás el layout forzado: leer una medida justo después de escribir un estilo.

Un solo hilo para todo

El JavaScript de una página se ejecuta en un único hilo, el hilo principal. Y ese hilo no es solo tuyo: el navegador lo usa también para calcular estilos, hacer el layout, pintar, despachar eventos y ejecutar los callbacks de los temporizadores. Mientras tu código se ejecuta, nada de eso puede ocurrir. Si un cálculo tarda 200 ms, la página está 200 ms sin responder a clics y sin pintar nada nuevo.

Para decidir qué se ejecuta y cuándo, el navegador sigue un algoritmo definido en el estándar HTML: el event loop (bucle de eventos). Es un bucle que, simplificando mucho, hace esto una y otra vez:

  1. Coge una tarea de la cola y la ejecuta entera.
  2. Ejecuta todas las microtareas pendientes.
  3. Si toca, pinta un frame: callbacks de requestAnimationFrame, estilo, layout, pintado y composición.

Esta lección desmonta cada paso, con experimentos en Chrome, porque de este orden depende todo lo que harás en el módulo 2: un bucle de animación bien hecho es, literalmente, un buen uso del event loop.

Cuando una animación tiembla, se congela o da saltos, la causa casi nunca es el código que dibuja: es cuándo se ejecuta. Una tarea demasiado larga, un temporizador que no está sincronizado con la pantalla o un bucle de promesas que no deja pintar. Si sabes qué hace el event loop, sabes dónde mirar.

La pila de llamadas

La pila de llamadas (call stack) es la lista de funciones que están ejecutándose ahora mismo, una encima de otra. Cuando llamas a una función, se apila; cuando termina, se desapila y el control vuelve a la de debajo. JavaScript ejecuta lo que está en la cima, y solo eso.

Cuando dibujarParticula se está ejecutando, la pila es frame → dibujarTodo → dibujarParticula. La pila tiene un tamaño máximo: una recursión sin final acaba en RangeError: Maximum call stack size exceeded (el mismo error que viste con Math.max(...array) gigantes en la lección 1.3). Lo importante para el event loop es un momento concreto: cuando la pila queda vacía. Solo entonces puede el navegador hacer otra cosa.

El momento en que se vacían las microtareas se llama punto de control de microtareas (microtask checkpoint), y ocurre cada vez que la pila de llamadas queda vacía. Fíjate en que no dice «al terminar cada tarea», sino «cada vez que la pila queda vacía», y la diferencia se nota:

Lo comprobé con dos oyentes de click en el mismo botón, cada uno de los cuales encola una microtarea:

  • Con un clic real del usuario, el resultado fue L1 M1 L2 M2: el navegador llama a cada oyente con la pila vacía debajo, así que al terminar el primero hay un punto de control y su microtarea se ejecuta antes que el segundo oyente.
  • Con boton.click() desde tu código, fue L1 L2 M1 M2: los oyentes se ejecutan encima de tu script, la pila nunca queda vacía entre ellos, y las dos microtareas esperan a que termine todo.

Disparar un evento desde código no es exactamente igual que el evento real. Rara vez importa, pero cuando importa (un test automático que «no reproduce» un fallo, por ejemplo) es desconcertante.

El frame: cuándo pinta el navegador

Un monitor de 60 Hz muestra una imagen nueva cada 16,7 ms. El navegador intenta producir un frame para cada refresco, y lo hace entre tareas: cuando toca pintar y el hilo está libre, ejecuta los pasos de «actualizar el renderizado». Medí los instantes de 20 callbacks seguidos de requestAnimationFrame en Chrome: estaban separados 16,6 o 16,7 ms, como un reloj (a 120 Hz serían 8,3 ms: la lección 2.3 se ocupa de eso).

Los pasos de un frame, en orden:

  1. Callbacks de requestAnimationFrame. Es tu oportunidad de cambiar el DOM, los estilos o dibujar en un canvas justo antes de que se pinte: por eso es el sitio del bucle de animación. Todos los callbacks del mismo frame reciben el mismo instante (dos callbacks recibieron exactamente 23,1 ms), y un requestAnimationFrame pedido dentro de un callback se ejecuta en el frame siguiente, no en este.
  2. Estilo: calcula qué reglas CSS se aplican a cada elemento.
  3. Layout: calcula la posición y el tamaño de cada caja. Después, se ejecutan los callbacks de ResizeObserver (comprobé en la lección 1.4 que llegaban después de los de rAF) y se actualizan los IntersectionObserver.
  4. Pintado: convierte las cajas en listas de órdenes de dibujo.
  5. Composición: combina las capas pintadas y las manda a la pantalla. Esta parte ocurre en otro hilo, el del compositor, con ayuda de la GPU. Recuerda este detalle: dentro de poco lo veremos en acción.

El pipeline de renderizado completo, con qué propiedades CSS disparan cada paso, es la lección 2.1. Aquí nos basta con saber cuándo ocurre: entre tareas, nunca en medio de una.

            Ejemplo 1.5.1 — Un programa con async/await, paso a paso
            
  
            async/await parece código síncrono, pero cada await parte la función en dos: lo que va después se ejecuta más tarde, como una microtarea (o después de una tarea, si lo que esperas tarda en resolverse). Predice el orden antes de ejecutar:
            
  
            

  
            
  
            Durante el script (una tarea). Se imprime 1. El setTimeout registra el temporizador A. La función async se llama y se ejecuta síncronamente hasta su primer await: imprime 3. En await null se suspende y encola su continuación como microtarea (la llamaremos C1). El script sigue: el then encola la microtarea «6», detrás de C1, y se imprime 7.
            
  
            Punto de control de microtareas. La cola es [C1, «6»]. C1 imprime 4 y llega al segundo await: crea una promesa que solo se resolverá cuando venza un temporizador B, registrado ahora (después que A), y se suspende otra vez. Después, «6» imprime 6. Cola vacía.
            
  
            Tareas. Vence A e imprime 2. Vence B: su callback resuelve la promesa, lo que encola la continuación C2 como microtarea; al terminar esa tarea se vacían las microtareas y C2 imprime 5.
            
  
            Resultado: 1 3 7 4 6 2 5, el mismo que dio Chrome. La lección: el código de una función async anterior al primer await es síncrono; cada await es un punto donde la función cede, y lo que cede depende de qué esté esperando.
            

            


            Una tarea larga lo congela todo… casi
            

            Si una tarea tarda mucho, el bucle no puede llegar al paso del frame: no hay callbacks de rAF, ni estilo, ni layout, ni pintado. Pero el paso de composición vive en otro hilo. Una animación CSS de transform u opacity puede ejecutarse entera en el compositor, sin el hilo principal. Lo comprobé grabando los frames que producía Chrome (con la herramienta de screencast del protocolo de DevTools) mientras un bucle bloqueaba el hilo principal 1,5 s: dos cajas con el mismo movimiento, una animada con @keyframes sobre transform y otra con JavaScript y rAF. Durante el bloqueo se grabaron 84 frames; en ellos, la caja de CSS siguió avanzando (de x = 415 a 625 y vuelta a 445) y la de JavaScript se quedó clavada en x = 400. Al terminar el bloqueo, la de JavaScript saltó a su sitio.
            

            Compruébalo tú. El botón ejecuta un bucle ocupado en el hilo principal de esta página, así que durante 1,5 s todo lo demás de la página (las otras demos, los botones, el resto del código) quedará congelado. (Los editores de código son iframes y en Chrome pueden seguir funcionando: se explica en el ejemplo 1.5.2.)

            Pulsa el botón con la animación de JavaScript «basada en el tiempo»: la bola cian se congela y, al terminar, salta a donde debería estar, porque su posición se calcula a partir del instante del frame. Cambia a «basada en frames» (x += paso en cada frame) y repite: al terminar el bloqueo, continúa desde donde se paró, con 1,5 s de retraso para siempre.             Síntoma: durante un momento (al cargar datos, al generar una malla, al procesar una imagen) la animación se detiene, los botones no responden y después todo da un salto.
            
  
            Causa: una tarea larga ocupa el hilo principal. Mientras no termine, el event loop no puede ejecutar callbacks de rAF, ni eventos, ni pintar. Solo sobreviven las animaciones que viven en el compositor (CSS sobre transform y opacity) y el propio desplazamiento de la página, que también lo gestiona el compositor mientras no haya listeners que lo bloqueen.
            
  
            Solución: trocea el trabajo en pedazos de pocos milisegundos y devuelve el control al event loop entre uno y otro, esperando al siguiente frame o creando una tarea nueva (ejercicio 1.5.2); mueve el cálculo pesado a un Web Worker; y para animaciones decorativas que no deben tropezar, usa CSS sobre transform/opacity. En DevTools, las tareas de más de 50 ms aparecen marcadas en rojo como long tasks (lección 1.7).
            

            


            
  
            Ejemplo 1.5.2 — Detectar tareas largas y trocearlas
            
  
            El navegador puede avisarte de cada tarea que pase de 50 ms con un PerformanceObserver de tipo "longtask". Aquí lo usamos para medir un cálculo pesado hecho de golpe y el mismo cálculo troceado:
            
  
            

  
            
  
            El observador. observe({ type: "longtask" }) pide al navegador un aviso por cada tarea de más de 50 ms. Cada entrada trae su duración (e.duration). Lo comprobé aparte: una tarea de 120 ms se notificó y una de 30 ms, no.
            
  
            De golpe. 120 millones de raíces cuadradas en una sola tarea: el observador informa de una tarea larga de la misma duración, y durante ese tiempo la página no pinta ni responde.
            
  
            Troceado. El mismo cálculo, en 60 trozos de dos millones, cediendo el hilo entre trozo y trozo con un MessageChannel (que crea una tarea nueva sin el mínimo de 4 ms de setTimeout). Ahora ninguna tarea supera los 50 ms (o casi ninguna, según tu máquina: si alguna los pasa, reduce el tamaño del trozo), y el tiempo total apenas cambia. El trabajo es el mismo; lo que cambia es que el event loop recupera el control decenas de veces, y en cada una puede pintar y atender eventos.
            
  
            Un detalle sobre los editores del curso: son iframes con sandbox. En un Chrome de escritorio con su configuración normal, cada uno corre en su propio proceso, con su propio hilo principal. Lo comprobé de dos maneras: con un bucle ocupado de 1,5 s dentro de un editor, los temporizadores de la página de la lección siguieron llegando cada 50 ms; y un observador de tareas largas dentro de un iframe no vio un bloqueo de 300 ms de la página. Así que un bucle infinito en un editor congela ese editor (el botón «Detener» lo destruye), no la lección. Pero es una optimización del navegador, no una garantía: en un Chrome con ese aislamiento desactivado (algunas herramientas de pruebas automáticas lo desactivan por defecto, y allí medí 1,5 s de congelación en la página) o en un dispositivo con poca memoria, los iframes pueden compartir hilo con la página, y entonces un bloqueo en uno se nota en todos.
            

            


            setTimeout no es un reloj
            

            setTimeout(fn, 0) no significa «ahora»
            

            Significa «encola una tarea cuando haya pasado al menos 0 ms». Se ejecutará cuando el event loop llegue a ella: después del código actual, después de todas las microtareas y, quizá, después de un frame. Además, el estándar HTML impone un mínimo de 4 ms cuando los temporizadores se anidan más de cinco niveles (un setTimeout dentro del callback de otro, y así sucesivamente). Lo medí encadenando setTimeout(paso, 0): las primeras vueltas tardaron entre 0 y 0,4 ms y, a partir de la séptima, unos 5 ms cada una. En 300 ms, una cadena de setTimeout(0) dio solo 67 vueltas.
            

            
  
            Si necesitas encadenar tareas rápido sin bloquear el hilo (para trocear un cálculo largo), hay alternativas que no sufren el mínimo. Un MessageChannel que se envía mensajes a sí mismo dio 114 155 vueltas en 300 ms, frente a las 67 de setTimeout(0). Y lo importante: durante 600 ms de vueltas con MessageChannel, el navegador siguió pintando unos 36 frames, porque cada vuelta es una tarea y entre tareas se puede pintar. Existe también await scheduler.yield(), la API moderna para ceder el hilo (143 905 vueltas en 300 ms), pero tiene un matiz que verás en el ejercicio 1.5.2: prioriza la continuación de tu código, y en mis pruebas apenas dejaba pintar.
            

            


            setTimeout frente a requestAnimationFrame
            

            Antes de requestAnimationFrame, las animaciones se hacían con setTimeout(frame, 16). Medí 20 vueltas de una cadena así: los intervalos fueron desde 16,2 hasta 18,8 ms, irregulares y sin relación con el refresco de la pantalla. Los de rAF, en la misma página, fueron 16,6 y 16,7 ms, clavados. Con setTimeout, algunos refrescos reciben dos actualizaciones y otros ninguna: la animación tiembla. rAF, además, se detiene cuando la pestaña no se ve (lo medimos más abajo) y recibe el instante exacto del frame. Para animar, siempre rAF.
            

            
  
            Síntoma: un código que registra un setTimeout(fn, 0) y un requestAnimationFrame(fn2) se comporta distinto de una ejecución a otra, o en otro ordenador.
            
  
            Causa: el estándar no fija si el navegador ejecuta antes la tarea del temporizador o el frame; depende de cuánto falte para el siguiente refresco. Lo medí repitiendo el puzzle clásico 40 veces: el timeout salió antes 21 veces y el rAF 19. Y justo después de un bloqueo de 100 ms, el rAF salió antes las 20 veces que lo probé, porque el frame iba con retraso.
            
  
            Solución: no dependas de ese orden. Si una cosa tiene que ocurrir antes de pintar, ponla en el callback de rAF; si tiene que ocurrir después de otra, encadénala explícitamente.
            

            


            
  
            Dentro de un callback de requestAnimationFrame ejecutas requestAnimationFrame(b) y Promise.resolve().then(m). ¿Cuándo se ejecutan b y m?
            
  
              
    
            • Los dos en este mismo frame, antes de pintar.
              m sí (es una microtarea, y se vacían al terminar cada callback de rAF), pero b no: los callbacks de rAF pedidos durante un frame se guardan para el siguiente.
              • 
    
            • m al terminar este callback, antes de pintar; b en el frame siguiente.
              Correcto: es el programa «rAF dentro de rAF» del simulador. Si no fuera así, un bucle de animación que se vuelve a pedir en cada frame nunca dejaría pintar.
              • 
    
            • Los dos en el frame siguiente.
              Una microtarea nunca espera a un frame: se ejecuta en cuanto la pila se vacía, que es al terminar el callback actual.
              • 
  
            

            


            Inanición por microtareas
            

            La regla «se vacían todas las microtareas, incluidas las nuevas» tiene un reverso: si cada microtarea encola otra, la cola nunca se vacía y el event loop nunca llega al frame. La página se congela exactamente igual que con un bucle while, aunque no haya ningún bucle a la vista. Lo medí dejando correr 600 ms una cadena de queueMicrotask que se volvía a encolar: en esos 600 ms se pintó 1 frame. La misma cadena hecha con setTimeout(0) pintó 36 frames, porque cada vuelta es una tarea nueva y entre tareas el navegador puede pintar.
            

            
  
            Síntoma: la página deja de pintar y de responder, aunque tu código no tiene ningún bucle largo; o una animación «asíncrona» hecha con promesas no se ve hasta que termina entera.
            
  
            Causa: una cadena de microtareas que no termina (una función async que hace await de promesas ya resueltas en un bucle, o queueMicrotask recursivo). Las microtareas nunca ceden el paso al frame.
            
  
            Solución: para ceder de verdad hay que crear una tarea (await new Promise((r) => setTimeout(r, 0)), un MessageChannel) o esperar al siguiente frame (await new Promise(requestAnimationFrame)). Un await de algo ya resuelto no cede nada.
            

            


            Relojes: performance.now() frente a Date.now()
            

              
  
            • performance.now(): milisegundos desde que empezó a cargarse la página (performance.timeOrigin), con decimales. Es monótono: nunca va hacia atrás, aunque cambie la hora del sistema. Su resolución está recortada a propósito para dificultar ataques de temporización: medí saltos mínimos de 0,1 ms (100 µs). Las páginas con aislamiento de origen cruzado (crossOriginIsolated, que requiere cabeceras especiales del servidor) tienen resolución más fina, de 5 µs según la documentación; una página abierta con file:// no lo está.
              • 
  
            • Date.now(): milisegundos enteros desde el 1 de enero de 1970, según el reloj del sistema. Sirve para fechas; no para medir duraciones, porque si el sistema ajusta la hora (sincronización de red, cambio manual), puede saltar hacia delante o hacia atrás.
              • 
  
            • El argumento de rAF es un instante en el mismo reloj que performance.now() (y que e.timeStamp de los eventos): el comienzo del frame. Dentro del callback, performance.now() ya es algo mayor (entre 0,4 y 2,5 ms en mis medidas), porque el frame empezó antes de llamar a tu función. Para animar, usa el argumento: todos los callbacks del frame ven el mismo tiempo y todo se mueve sincronizado.
              • 

            


            
  
            Un reloj muy preciso permite medir cuánto tarda en leerse una posición de memoria, y eso es la base de ataques como Spectre, que deducen datos ajenos a partir de esos tiempos. Por eso los navegadores recortan la resolución de performance.now() y le añaden un pequeño ruido. Para animar da igual: 0,1 ms es cien veces más fino que un frame. Para medir el rendimiento de un trozo de código, en cambio, repite la operación muchas veces y mide el total; una sola medida de algo que tarda microsegundos no significa nada.
            

            


            Pestañas en segundo plano
            

            Cuando una pestaña no se ve, el navegador ahorra trabajo. Lo medí en Chrome con una página que contaba callbacks de rAF y vueltas de un setInterval de 100 ms, y que después pasaba a segundo plano (document.visibilityState = "hidden") durante 4 s:
            

            
  
            en primer plano (2 s)en segundo plano (4 s)
            
  
    
            callbacks de requestAnimationFrame1210: rAF se detiene por completo
            
    
            vueltas de setInterval(fn, 100)204, separadas ~1000 ms: como mucho una por segundo
            
              

            

            Según la documentación de Chrome, si la pestaña sigue oculta más de cinco minutos, las cadenas de temporizadores pueden limitarse todavía más (a una vez por minuto).
            

            Y no solo se frenan los temporizadores: el propio JavaScript de una pestaña oculta corre bastante más despacio. El playground «El mismo cálculo en tu CPU y en tu GPU» de la lección 4.1, que con la ventana a la vista tarda 0,9–1,2 s, tardó 2,4–3,0 s con la ventana minimizada (Chrome 154 en un Apple M1), y más de 5 s en un Chrome de uso diario con la ventana detrás de otras. No lo hemos aislado; lo más probable es que Chrome baje la prioridad del proceso de una pestaña oculta y el sistema operativo le dé menos CPU. Moraleja: no midas rendimiento con la pestaña en segundo plano.
            

            Para tu bucle de animación, lo importante es esto:
            

            
  
            Síntoma: cambias de pestaña, vuelves al cabo de un rato y los objetos aparecen de golpe muy lejos, la física explota o un contador ha avanzado de golpe.
            
  
            Causa: mientras la pestaña estaba oculta, rAF no se ejecutó. En el primer frame al volver, el tiempo transcurrido desde el frame anterior (dt) son decenas de segundos, y la simulación lo aplica de una vez. (La misma causa en un bucle que se duerme cuando nada se mueve: «Cada transición empieza con un salto (en un bucle que se duerme)», 7.3.)
            
  
            Solución: limita dt (por ejemplo, Math.min(dt, 0.1), como hacen las demos de este curso) o pausa la animación en el evento visibilitychange y reinicia el reloj al volver. Y nunca uses temporizadores para llevar la cuenta del tiempo: en segundo plano se ralentizan.
            

            


            
  
            Tu juego calcula dt como el tiempo desde el frame anterior. Pasas 30 segundos en otra pestaña y vuelves. Sin ningún límite, ¿qué dt recibe el primer frame?
            
  
              
    
            • Unos 16,7 ms, como siempre.
              rAF no se ejecutó mientras la pestaña estaba oculta, así que el frame anterior fue hace unos 30 s.
              • 
    
            • Unos 30 segundos.
              Exacto. rAF se detiene en segundo plano (medimos 0 callbacks en 4 s) y el primer frame al volver ve todo el hueco. Por eso se limita dt o se pausa en visibilitychange.
              • 
    
            • Unos 30 frames de 1 segundo cada uno, porque rAF sigue a una vez por segundo.
              Eso le pasa a setInterval (se limita a una vez por segundo), no a rAF, que se detiene por completo.
              • 
  
            

            


            Otros hilos: Web Workers y OffscreenCanvas
            

            El hilo principal no es el único disponible. Un Web Worker ejecuta JavaScript en otro hilo, sin acceso al DOM, y se comunica con la página por mensajes (postMessage); los ArrayBuffer se pueden transferir sin copiarlos (lección 1.6). Es el sitio para cálculos pesados: generar una malla, simular miles de partículas en CPU, decodificar datos. Y con OffscreenCanvas, un worker puede incluso dibujar con WebGL2 en un canvas de la página, sin tocar el hilo principal. Lo comprobé con un worker creado a partir de un Blob, que recibió el canvas con transferControlToOffscreen() y obtuvo un contexto webgl2.
            

            
  
            Con file://, new Worker("trabajador.js") falla: SecurityError: Failed to construct 'Worker': Script at 'file:///…/trabajador.js' cannot be accessed from origin 'null'. Servida por HTTP, la misma página funcionó. El truco para file:// es crear el worker desde un Blob con el código en un string (new Worker(URL.createObjectURL(new Blob([codigo])))), que sí funcionó. El porqué de ese «origin 'null'», en la lección 1.7.
            

            


            Leer una medida justo después de escribir un estilo
            

            
  
            Cuando cambias un estilo, el navegador no recalcula nada en ese momento: marca el layout como «sucio» y lo recalcula una sola vez, en el siguiente frame. Pero si justo después lees una medida (offsetWidth, getBoundingClientRect(), getComputedStyle…), la respuesta tiene que ser correcta, así que el navegador se ve obligado a hacer el layout en ese instante, de forma síncrona, dentro de tu tarea. Es un layout forzado. Uno suelto no importa; alternar escrituras y lecturas en un bucle obliga a un layout por vuelta. A esto se le llama layout thrashing.
            

            

            


              
  
            1. En la primera vuelta, offsetWidth encuentra el layout al día. Pero la escritura de style.width lo ensucia, y el offsetWidth de la vuelta siguiente obliga a recalcularlo. Con 500 elementos, 500 layouts. Lo medí: 80 ms.
              2. 
  
            2. Todas las lecturas seguidas: la primera puede forzar un layout, las demás ya lo encuentran calculado.
              3. 
  
            3. Todas las escrituras seguidas: solo ensucian el layout, que se recalculará una vez, en el frame. Mismo resultado: 1 ms. El mismo trabajo, ochenta veces más rápido, solo por el orden, cuando a 60 fps tienes 16,7 ms por frame.
              4. 

            

            

            
  
            Síntoma: actualizar unos cientos de elementos por frame (barras, etiquetas, posiciones) tarda decenas de milisegundos, y en el panel Performance aparecen muchos bloques morados de «Layout» dentro de tu función.
            
  
            Causa: dentro del bucle se alternan escrituras de estilo y lecturas de medidas: cada lectura fuerza un layout síncrono.
            
  
            Solución: separa las fases: primero todas las lecturas, después todas las escrituras. Mejor aún, evita leer del DOM en el bucle de animación: guarda tú las medidas en variables y actualízalas con ResizeObserver. Y para mover cosas, transform, que no necesita layout. Lo verás a fondo en la lección 2.1.
            

            


            Ejercicios
            


            
  
            Ejercicio 1.5.1 — Predice el orden
            
  
            Sin ejecutar antes, escribe en prediccion el orden en que se registrarán los números. Después ejecuta: la consola compara tu predicción con el orden real y dice si has acertado. Si fallas, repasa las reglas (o reproduce el programa mentalmente en el simulador) antes de mirar la solución.
            
  
            


  
            
  
            Pista 1
            Primero, todo lo síncrono del script. Después, todas las microtareas (y las que se encolen mientras). Después, las tareas, de una en una, con sus microtareas detrás de cada una.
            
  
            Pista 2
            Hay tres temporizadores de 0 ms. ¿En qué orden se registran? Uno de ellos se registra dentro de una microtarea, es decir, después de que termine el script.
            
  
            Solución explicada
    
            El orden real es 1 8 3 5 2 6 7 4.
            
    
              
      
            1. Script (una tarea): se registran 1 y 8; por el camino se crean el temporizador «2», la microtarea del then y el temporizador «6».
              2. 
      
            2. Punto de control de microtareas: el then registra 3, crea el temporizador «4» (el tercero, registrado después que «2» y «6») y encola la microtarea «5», que se ejecuta en este mismo punto de control: 5.
              3. 
      
            3. Tareas, de una en una: los temporizadores vencen en el orden en que se registraron. «2» registra 2. «6» registra 6 y encola «7», que se ejecuta al terminar esa tarea, antes que la siguiente: 7. Por último, «4»: 4.
              4. 
    
            
    
            La trampa habitual es poner el 4 antes que el 2 («se registró dentro del primer then») o el 7 al final («es de una promesa, va después de los timeouts»). La regla que lo resuelve todo: tras cada tarea se vacían las microtareas.
            
  
            

            


            
  
            Ejercicio 1.5.2 — La barra de progreso que no se mueve
            
  
            El código procesa 40 lotes de trabajo (cada uno, un cálculo de unos 15 ms) y actualiza una barra de progreso después de cada lote. Pero la barra salta de 0 al 100 % de golpe y la bola de al lado se congela mientras tanto. Reescribe procesar para que la barra avance de verdad y la bola siga moviéndose, cediendo el control al event loop entre lote y lote. La consola debe mostrar muchos frames pintados durante el trabajo (ahora muestra 0 o 1).
            
  
            




  
            
  
            Pista 1
            Mientras el for se ejecuta, ¿puede el event loop llegar al paso de pintar? ¿Cuántas tareas hay ahí?
            
  
            Pista 2
            Convierte procesar en una función async y, tras cada lote, haz await de una promesa que se resuelva en el próximo frame. Cuidado: await Promise.resolve() solo crea una microtarea, y eso no deja pintar.
            
  
            Solución explicada
    
            En el original, los 40 lotes (unos 600 ms) se ejecutan dentro de una sola tarea. Aunque la anchura de la barra cambia 40 veces, el navegador no pinta hasta que la tarea termina, y entonces solo ve el último valor: 100 %. Por eso la consola dice que no se pintó ningún frame (a lo sumo uno) y la bola se congela.
            
    
            La solución convierte procesar en async y, tras cada lote, hace await ceder(), una promesa que se resuelve en el siguiente callback de requestAnimationFrame. La función se suspende ahí, la tarea actual termina, el navegador pinta el frame (con la barra en su nuevo ancho y la bola en su sitio) y, en ese frame, la función continúa con el lote siguiente. Un lote por frame: la consola pasa a mostrar unos 40 frames pintados.
            
    
            ¿Por qué no scheduler.yield(), la API «oficial» para ceder? Medí las cinco formas de ceder con estos mismos 40 lotes de 15 ms:
            
    
            
      
            Tras cada lote…tiempo totalframes pintados
            
      
        
            await Promise.resolve()600 ms0 (una microtarea no cede nada)
            
        
            await scheduler.yield()601 ms5
            
        
            MessageChannel603 ms37
            
        
            requestAnimationFrame664 ms40
            
        
            setTimeout(0)778 ms46 (y el mínimo de 4 ms alarga el total)
            
                  
    
            
    
            scheduler.yield() pone la continuación de tu código por delante de las demás tareas; según su documentación, sirve para que el navegador pueda atender la entrada del usuario, pero en Chrome casi nunca dejó pintar. Para que se vea el progreso, cede hasta el frame (rAF) o con una tarea (MessageChannel). El coste es un poco de tiempo total extra, a cambio de una página que responde. Para cálculos todavía más pesados, un Web Worker los saca del hilo principal del todo.
            
  
            

            


            
  
            Ejercicio 1.5.3 — El bucle que fuerza el layout
            
  
            La función ajustar pone a cada una de las 400 barras una altura proporcional a su anchura. Funciona, pero es muy lenta. Reescríbela para que haga exactamente lo mismo mucho más rápido, sin cambiar el resultado final. La consola mide el tiempo y comprueba que las alturas finales son idénticas.
            
  
            




  
            
  
            Pista 1
            ¿Qué le pasa al layout cuando escribes style.height? ¿Y qué tiene que hacer el navegador cuando, justo después, lees offsetWidth de la siguiente barra?
            
  
            Pista 2
            Separa el bucle en dos: uno que solo lee y guarda los anchos en un array, y otro que solo escribe.
            
  
            Solución explicada
    
            Cada b.style.height = … invalida el layout; la lectura de offsetWidth de la barra siguiente obliga al navegador a recalcularlo en ese momento. Son 400 layouts forzados, uno por vuelta. Da igual que la altura no afecte al ancho: el navegador no puede saberlo sin recalcular (las barras están en un contenedor flexible que reparte filas).
            
    
            La solución lee primero todos los anchos, con un único layout (el del primer offsetWidth; los demás ya encuentran el layout al día), y después escribe todas las alturas, lo que solo marca el layout como sucio una vez: se recalculará en el siguiente frame, como siempre. Mismo resultado (la comprobación da la misma suma), en una fracción del tiempo.
            
  
            

            


            
  
            Ejercicio 1.5.4 — Un cronómetro que no pierde el tiempo
            
  
            Este cronómetro suma 10 ms en cada vuelta de un setInterval de 10 ms. A mitad de la medida, un trabajo pesado bloquea el hilo 300 ms (simula, por ejemplo, un cálculo al cargar un nivel). Al final, compara con el tiempo real: se ha retrasado. Arréglalo para que el valor mostrado sea correcto al milisegundo, y para que el número en pantalla se actualice con requestAnimationFrame en lugar del setInterval. Al terminar, la consola debe mostrar una diferencia de 0 ms (o casi) con el tiempo real.
            
  
            




  
            
  
            Pista 1
            ¿Cuántas vueltas del setInterval caben en los 300 ms de bloqueo? ¿Cuántas se ejecutan después, cuando el hilo se libera?
            
  
            Pista 2
            No cuentes el tiempo: guarda el instante inicial y resta, en cada actualización, performance.now() − inicio.
            
  
            Solución explicada
    
            Por qué se retrasa. El cronómetro supone que cada vuelta del intervalo son exactamente 10 ms. No lo son: cada vuelta llega algo tarde, y sobre todo, durante los 300 ms de bloqueo no puede ejecutarse ninguna. Cuando el hilo se libera, el navegador no ejecuta de golpe las 30 vueltas perdidas: un intervalo no acumula vueltas pendientes. El cronómetro pierde, así, casi todo el bloqueo. Y en una pestaña en segundo plano, con el intervalo limitado a una vuelta por segundo, perdería casi todo el tiempo.
            
    
            La solución no cuenta nada: en cada frame mide performance.now() − inicioReal, un reloj monótono que sigue avanzando pase lo que pase. Aunque se pierdan frames durante el bloqueo, el siguiente frame muestra el valor correcto. La actualización en pantalla pasa a requestAnimationFrame: una vez por refresco, sincronizada con la pantalla (con setInterval de 10 ms se hacían actualizaciones que nadie llegaba a ver) y detenida si la pestaña está oculta.
            
    
            Es el mismo principio del ejercicio 1.3.2 y del ejemplo 1.3.2: el tiempo se calcula a partir de una fuente fiable, no se acumula a base de sumar pasos que suponemos iguales.
            
  
            

            


            
  
              
    
            • Un solo hilo para tu JavaScript, los eventos, el estilo, el layout y el pintado. El event loop: una tarea, todas las microtareas, y un frame si toca.
              • 
    
            • Tareas: scripts, temporizadores, eventos, mensajes; una por vuelta. Microtareas: promesas, await, queueMicrotask; todas, cada vez que la pila se vacía (también entre los oyentes de un evento real, pero no con el.click()).
              • 
    
            • Un frame: callbacks de rAF (todos con el mismo instante; los pedidos durante el frame, al siguiente), estilo, layout, ResizeObserver, pintado y composición (en el hilo del compositor).
              • 
    
            • El orden entre setTimeout(0) y rAF no está garantizado. setTimeout(0) tiene un mínimo de 4 ms cuando se anida más de cinco niveles (desde la séptima vuelta de una cadena); MessageChannel y scheduler.yield() no.
              • 
    
            • Una tarea larga congela las animaciones de JavaScript, pero no las de CSS sobre transform/opacity en el compositor. Trocea el trabajo cediendo con una tarea; un bucle de microtareas no cede nada.
              • 
    
            • performance.now() es monótono (resolución de 0,1 ms sin aislamiento); Date.now() es para fechas. En segundo plano rAF se detiene, los intervalos bajan a uno por segundo y hasta el cálculo va más lento: limita dt y no midas tiempos así.
              • 
    
            • Leer una medida justo después de escribir un estilo fuerza un layout síncrono: primero todas las lecturas, después todas las escrituras.
