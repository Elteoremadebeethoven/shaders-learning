CSS esencial: caja, posición y transformaciones

CSS decide dónde está cada caja y cómo se ve. Aquí aprendes el modelo con el que calcula el navegador (cascada, caja, posición, apilamiento, unidades) y, sobre todo, transform: la propiedad con la que vas a animar, que es literalmente una multiplicación de matrices.

⏱ 85 minRequisitos: 1.1

Al terminar esta lección

  • Sabrás qué regla gana cuando varias compiten (cascada y especificidad) y cómo leer desde JavaScript el valor que ganó.
  • Calcularás el tamaño real de una caja (content, padding, border, margin, box-sizing) y sabrás qué mide cada una de offsetWidth, clientWidth y getBoundingClientRect().
  • Colocarás elementos con position sabiendo cuál es su bloque contenedor, y entenderás por qué z-index: 9999 a veces no sirve de nada.
  • Elegirás unidades y colores sabiendo qué son de verdad: un píxel CSS no es un píxel de la pantalla.
  • Dominarás transform: sus funciones, transform-origin, por qué el orden importa (se aplican de derecha a izquierda) y por qué no mueve a los vecinos.
  • Usarás variables CSS como canal entre JavaScript y CSS.

Qué tiene que ver CSS con animar

Animar en la web es, casi siempre, una de dos cosas: cambiar propiedades CSS de un elemento a lo largo del tiempo (lecciones 2.2 y 2.7), o dibujar dentro de un canvas que CSS coloca en la página (2.6 y todo el módulo 5). En ambos casos necesitas saber exactamente dónde acaba cada caja y cuánto mide: el canvas a pantalla completa, la interfaz superpuesta al WebGL, el botón que tiene que quedar encima.

Y hay una razón más: no todas las propiedades cuestan lo mismo. Cambiar width obliga al navegador a recalcular la posición de media página; cambiar transform no mueve a nadie y, a menudo, lo resuelve la GPU sin tocar el hilo principal. Por eso la mitad de esta lección es preparación general y la otra mitad es transform a fondo. El porqué del coste lo verás en la lección 2.1, y una demostración en vivo en la 1.5.

Cómo gana una regla: selectores, cascada y especificidad

Una regla CSS es un selector (a qué elementos se aplica) y una lista de declaraciones propiedad: valor:

Los selectores que vas a usar en este curso son pocos: tipo (canvas), clase (.fondo), id (#lienzo), atributo ([data-activo]), descendiente (.escena canvas: un canvas dentro de .escena, a cualquier profundidad), hijo directo (.escena > canvas), pseudoclases (:hover, :first-child) y pseudoelementos (::before). Se combinan pegados: p.rojo.grande es un p con las dos clases.

Cuando varias reglas le dan valor a la misma propiedad del mismo elemento, la cascada decide cuál gana, comparando en este orden:

  1. Importancia: una declaración con !important gana a las que no lo tienen.
  2. Especificidad del selector: un trío (ids, clases, tipos) que se compara columna a columna, como un número de tres cifras en el que ninguna columna «se lleva» a la siguiente. Los atributos y las pseudoclases cuentan como clases; los pseudoelementos, como tipos. El atributo style="…" del HTML gana a cualquier selector.
  3. Orden: a igual especificidad, gana la regla que aparece después.

Lo comprobé con cinco párrafos y estas reglas, leyendo el color resultante con getComputedStyle:

ReglaEspecificidad¿Quién gana?
#p1 { color: blue }(1, 0, 0)el id gana a p.rojo.grande y a .rojo: azul
p.rojo.grande { color: green }(0, 2, 1)gana a .rojo y a div p: verde
.rojo { color: red }(0, 1, 0)una clase gana a dos tipos (div p): rojo
div p { color: rgb(1,2,3) }(0, 0, 2)solo gana si nadie más opina

Además de la cascada está la herencia: algunas propiedades, como color o font-size, pasan de padres a hijos si el hijo no tiene valor propio; otras, como width, margin o background, no se heredan. Las palabras clave inherit, initial y unset fuerzan cada comportamiento.

El resultado final de todo esto se lee desde JavaScript con getComputedStyle(el), que devuelve los valores ya resueltos: longitudes en px, colores normalizados. Lo usarás mucho, y en la lección 1.4 veremos su diferencia con el.style.

Un botón tiene class="btn primario" e id="enviar". Reglas: .btn.primario { color: white }, #enviar { color: black }, button.btn.primario { color: yellow }. ¿De qué color es el texto?

  • Amarillo, porque su selector es el más largo.
    button.btn.primario tiene especificidad (0, 2, 1): dos clases y un tipo. La longitud no importa; se comparan las columnas empezando por los ids.
  • Negro.
    Sí: #enviar es (1, 0, 0). La columna de ids se compara primero, y 1 > 0 decide sin mirar las demás columnas. Ni diez clases le ganan a un id.
  • Blanco, porque es la primera regla.
    El orden solo desempata cuando la especificidad es idéntica. Además, en caso de empate gana la última, no la primera.

El modelo de caja

Cada elemento genera una caja rectangular con cuatro capas, de dentro a fuera: el contenido, el relleno (padding), el borde (border) y el margen (margin). El fondo se pinta bajo el contenido, el relleno y el borde; el margen siempre es transparente y solo separa la caja de sus vecinas.

box-sizing: qué mide width

Aquí está la primera trampa: por defecto (box-sizing: content-box), width es el ancho del contenido, y el relleno y el borde se suman por fuera. Con box-sizing: border-box, width es el ancho hasta el borde, y el contenido encoge para hacer sitio. Medí dos cajas con width: 200px; padding: 10px; border: 5px:

content-boxborder-box
getComputedStyle(el).width"200px""200px"
ancho del contenido200170 (200 − 2·10 − 2·5)
clientWidth (contenido + padding)220190
offsetWidth (hasta el borde)230200

Con border-box, lo que escribes es lo que ocupa: por eso casi todos los proyectos empiezan con * { box-sizing: border-box; }, y este curso también (está en la primera línea de reglas de su hoja de estilos). Fíjate en que getComputedStyle(el).width devuelve "200px" en los dos casos: es la propiedad width ya resuelta, y su significado depende del box-sizing (el contenido con content-box, hasta el borde con border-box). No es una medida de la caja como offsetWidth: con content-box no te dice nada de cuánto añaden el relleno y el borde.

Los márgenes verticales se fusionan

Una rareza con historia tipográfica: cuando dos márgenes verticales se tocan, no se suman, se fusionan (margin collapsing) y queda el mayor. Dos bloques seguidos, uno con margin: 20px 0 y otro con margin: 30px 0, quedaron separados 30 px, no 50. Pensado para párrafos (el espacio entre dos párrafos es el de uno, no el doble), sorprende cuando maquetas.

La versión traicionera ocurre entre padre e hijo:

Síntoma: le pones margin-top: 40px al primer hijo para separarlo del borde de su contenedor, y lo que baja es el contenedor entero: el hijo sigue pegado arriba del padre y el fondo del padre empieza 40 px más abajo.

Causa: si entre el margen del padre y el del primer hijo no hay borde, relleno ni contenido, los dos márgenes se fusionan y el del hijo «sale» por arriba del padre. Lo medí: el borde superior del padre y el del hijo quedaron a la misma altura.

Solución: dale al padre un padding-top (o un borde), o conviértelo en un contexto de formato de bloque: display: flow-root (lo más limpio), overflow: hidden o display: flex. Con overflow: hidden comprobé que el hijo quedaba 40 px por debajo del borde del padre, como se esperaba. En flex y grid los márgenes nunca se fusionan.

Ejemplo 1.2.1 — ¿Cuánto mide de verdad esta caja?

Un panel de controles tiene width: 50%, padding: 12px 16px, border: 3px solid y margin: 10px, sin box-sizing, dentro de un contenedor de 600 px de ancho de contenido. ¿Cuánto ocupa en horizontal? Primero a mano, después lo comprobamos.

  1. El contenido. Un porcentaje en width se calcula sobre el ancho del contenido del bloque contenedor: 50 % de 600 = 300 px.
  2. Hasta el borde (offsetWidth). Con content-box, el relleno y el borde se suman: 300 + 16 + 16 + 3 + 3 = 338 px.
  3. Sin el borde (clientWidth). 300 + 16 + 16 = 332 px.
  4. Con los márgenes. 338 + 10 + 10 = 358 px de espacio horizontal reservado.
  5. Con border-box. width pasa a ser el ancho hasta el borde: offsetWidth = 300 y el contenido encoge a 300 − 32 − 6 = 262 px.

La consola confirma las cuentas: 338 / 332 con content-box y 300 / 294 con border-box. Y la última línea muestra el matiz de antes: con scale(0.5), offsetWidth sigue en 300 mientras que rect.width pasa a 150. Mira también el valor de getComputedStyle(panel).width: con border-box dice "300px", el ancho hasta el borde, porque devuelve la propiedad width tal como se interpreta con ese box-sizing.

display: cómo fluyen las cajas

La propiedad display decide cómo se coloca una caja respecto a las demás. Cinco valores cubren el 95 % de lo que harás:

  • block (div, p, section…): ocupa todo el ancho disponible y se apila verticalmente. width y height funcionan.
  • inline (span, a, em…): fluye dentro del texto, como una palabra. width y height se ignoran, y el relleno y los márgenes verticales no empujan las líneas. Lo medí: un span con width: 300px; height: 300px; padding: 20px midió 77 × 57 px, y el párrafo que lo contenía siguió midiendo 24 px de alto (el relleno se pinta, pero invade las líneas vecinas).
  • inline-block: fluye como una palabra pero acepta width y height. Con un detalle: los nodos de texto de espacios de la lección 1.1 se convierten en un espacio visible entre elementos. Medí 4,45 px de hueco entre dos inline-block separados por un salto de línea (con Arial a 16 px, lo que mide un espacio) y 0 px cuando iban pegados en el HTML.
  • none: la caja desaparece del todo; no ocupa sitio. (visibility: hidden, en cambio, la oculta pero conserva su hueco).
  • flex: convierte al elemento en un contenedor que reparte a sus hijos en una fila (o columna). Lo básico, abajo.

Síntoma: el contenedor de tu canvas mide unos píxeles más de alto que el canvas, y aparece una franja del color de fondo debajo.

Causa: canvas (como img y video) es inline por defecto: se coloca sobre la línea base del texto, como una letra, y debajo queda el hueco reservado para los trazos descendentes de letras como «g» o «p». Lo medí: un div con un canvas de 100 px dentro midió 104 px.

Solución: canvas { display: block; } (con eso el div pasó a medir 100 px), o vertical-align: top. Es la primera línea del CSS de casi cualquier proyecto con canvas.

Flexbox en cinco propiedades

El eje principal es el de flex-direction (fila por defecto) y el cruzado, el perpendicular. justify-content reparte en el principal, align-items alinea en el cruzado, gap separa y flex: 1 hace que un hijo crezca. Con eso montas el 90 % de las interfaces alrededor de un canvas. Y una trampa específica del canvas:

Síntoma: un canvas con flex: 1 se sale de su contenedor (aparece scroll horizontal) en lugar de ocupar el espacio que le queda.

Causa: los hijos de un flex tienen min-width: auto: no encogen por debajo del ancho de su contenido. Y el «contenido» de un canvas es su búfer: con width="600", el canvas se negó a bajar de 600 px aunque solo quedaban 250 (medido). Peor aún, si ajustas el búfer al tamaño de la caja (como en el ejercicio 1.1.4), el canvas ya no encogerá nunca al estrechar la ventana.

Solución: min-width: 0 en el canvas (con eso midió los 250 px disponibles). En grid, usa columnas minmax(0, 1fr).

position: sacar cajas del flujo

Por defecto las cajas están en el flujo normal: cada bloque debajo del anterior. position cambia eso, junto con top, right, bottom, left (o inset, que los fija los cuatro a la vez):

  • static (por defecto): en el flujo; top/left se ignoran.
  • relative: se desplaza visualmente respecto a su sitio, pero su hueco original se conserva. Lo medí: con left: 30px; top: 10px, la caja se dibujó en (30, 10) y el bloque siguiente empezó donde habría empezado sin desplazamiento. Su uso principal no es moverse: es convertirse en bloque contenedor de sus hijos absolute.
  • absolute: sale del flujo (los vecinos actúan como si no existiera) y se coloca respecto a su bloque contenedor: el ancestro más cercano con position distinto de static. Si no hay ninguno, respecto al documento.
  • fixed: se coloca respecto a la ventana y no se mueve con el scroll. Ideal para un canvas de fondo a pantalla completa: position: fixed; inset: 0.
  • sticky: se comporta como relative hasta que el scroll lo lleva a su top, y entonces se queda pegado mientras su contenedor siga a la vista.

El detalle que no suele contarse: transform (y también filter y perspective) convierte a un elemento en bloque contenedor de sus descendientes absolute y… fixed. Lo medí con un contenedor en (100, 160) y un hijo con position: fixed; top: 10px; left: 10px:

Contenedorhijo absolute enhijo fixed en
sin position(10, 10) del documento(10, 10) de la ventana
position: relative(110, 170): relativo al contenedor(10, 10) de la ventana
transform: translateX(0) (una transformación que no hace nada)(110, 170)(110, 170), y se desplaza con el scroll

Síntoma: un panel o un canvas con position: fixed se desplaza con la página o aparece en un sitio raro.

Causa: algún ancestro tiene transform, filter, perspective o will-change: transform. Eso lo convierte en el bloque contenedor del elemento fijo, que pasa a ser fijo respecto a ese ancestro, no respecto a la ventana. Pasa mucho cuando envuelves la página en un contenedor animado.

Solución: saca el elemento fijo fuera del ancestro transformado (por ejemplo, como hijo directo de <body>) o quita la transformación del ancestro cuando no la necesites.

Ejemplo 1.2.2 — Un rótulo centrado encima del canvas

Queremos una interfaz superpuesta (HUD) a un canvas: un rótulo centrado exactamente en el medio, y un contador de FPS en la esquina superior derecha. Es el esqueleto de cualquier escena WebGL con interfaz.

1. position: relative en .escena no la mueve: la convierte en el bloque contenedor de los absolute de dentro. Sin esa línea, el rótulo se colocaría respecto al documento.

2 y 3. left: 50%; top: 50% ponen la esquina superior izquierda del rótulo en el centro. Los porcentajes de left y top se refieren al bloque contenedor.

4. Aquí está el truco: los porcentajes de translate() se refieren a la propia caja del elemento. translate(-50%, -50%) la retrocede la mitad de su ancho y la mitad de su alto, sea cual sea su tamaño. Lo comprobé aparte con una caja de 100 px de ancho en un contenedor de 600: con left: 50% y translate(-50%) quedó en x = 250, con el centro en 300. La consola del editor muestra que los dos centros coinciden.

5. Un último detalle, que se ve al quitar white-space: nowrap: con left: 50%, a un elemento absolute solo le queda la mitad del ancho del contenedor para su contenido, y un texto largo se parte en dos líneas (este rótulo mide 253 px en una sola línea, pero en una escena de 350 px, con left: 50%, solo dispone de 175). Con nowrap el rótulo conserva su tamaño natural y el translate(-50%, -50%) lo centra de verdad.

Prueba a escribir mal una propiedad del rótulo, por ejemplo postion: absolute, y vuelve a ejecutar: el rótulo cae al flujo normal, debajo del canvas (y como el transform sigue aplicándose, medio rótulo queda fuera de la ventana por la izquierda), y no aparece ningún error en ninguna parte. Igual que el HTML, CSS no lanza errores: descarta en silencio cada declaración que no entiende y sigue con la siguiente. En el panel Elements de DevTools, esas declaraciones aparecen tachadas con un aviso; es el primer sitio donde mirar cuando «un estilo no se aplica».

Contextos de apilamiento: por qué z-index «no funciona»

Cuando dos cajas se solapan, ¿cuál se ve encima? Sin hacer nada, la que va después en el HTML, y las posicionadas por encima de las que no lo están. z-index permite cambiarlo, con dos condiciones que casi nadie conoce del todo:

  1. Solo funciona en elementos posicionados (position distinto de static) o en hijos de un flex o un grid. En un bloque normal se ignora: una caja estática con z-index: 50 quedó debajo de una caja con position: relative y sin z-index, que iba después. Al darle position: relative a la primera, pasó arriba. En cambio, un hijo de un flex con z-index: 3 y sin position sí quedó encima de su vecino.
  2. Solo compite dentro de su contexto de apilamiento. Un contexto de apilamiento es un grupo de cajas que se pinta como una unidad, como una capa de un programa de dibujo con su propio orden interno. Los z-index de dentro solo ordenan a los miembros del grupo; hacia fuera, el grupo entero tiene el z-index de su raíz.

Lo reproduje: A con position: absolute; z-index: 1, su hijo A1 con z-index: 9999, y B con z-index: 2. En la zona donde A1 y B se solapan, document.elementFromPoint() devolvió B. Y no hace falta un z-index para crear un contexto: con opacity: 0.99 en el padre (y sin z-index), un hijo con z-index: 100 quedó debajo de un vecino con z-index: 5. Crean contexto de apilamiento, entre otros:

  • un elemento posicionado (absolute o relative) con z-index distinto de auto; fixed y sticky siempre;
  • opacity menor que 1, transform, filter, mix-blend-mode distintos de sus valores por defecto;
  • will-change: transform u opacity, e isolation: isolate (que existe solo para eso);
  • un hijo de flex o grid con z-index.

Síntoma: un menú, un tooltip o una etiqueta sobre tu canvas queda tapado por otro elemento, subas lo que subas su z-index.

Causa: o el elemento no está posicionado (y su z-index se ignora), o un ancestro suyo crea un contexto de apilamiento (z-index, opacity, transform, filter…) que está por debajo del elemento que lo tapa. Su z-index solo compite dentro de ese ancestro.

Solución: sube de la hoja a la raíz buscando quién crea contexto (en DevTools, el panel Layers o el inspector de estilos computados ayudan). Sube el z-index de ese ancestro, quita la propiedad que crea el contexto o mueve el elemento fuera de él.

Como transform crea un contexto de apilamiento (y un bloque contenedor para los fixed), empezar a animar un elemento puede cambiar el orden de pintado de sus descendientes o recolocar a un hijo fixed. Mismo aviso para el viejo truco de «forzar la GPU» con transform: translateZ(0) o will-change: transform: además de lo que buscabas, creas un contexto nuevo. Si algo «salta» justo cuando empieza una animación, sospecha de esto.

Unidades: qué mide cada una

El píxel CSS no es un píxel de tu pantalla

px es una unidad de referencia, no un punto físico. En una pantalla «retina» con devicePixelRatio = 2, un píxel CSS ocupa 2 × 2 píxeles físicos; en un móvil con devicePixelRatio = 3, 3 × 3. Al maquetar no lo notas: todo se mide en px CSS y el navegador escala. Pero un canvas y WebGL trabajan con píxeles físicos, y ahí aparece el factor: por eso en el ejercicio 1.1.4 multiplicamos el búfer por devicePixelRatio. Además, ese valor no es constante: cambia si arrastras la ventana a otra pantalla y, según la documentación de MDN, también con el zoom del navegador. Compruébalo tú: ejecuta este editor, haz zoom con Ctrl/⌘ + + y pulsa ▶ otra vez.

Solución: usa width: 100% en los bloques y position: fixed; inset: 0 para un canvas a pantalla completa. Para medir el ancho útil desde JavaScript, document.documentElement.clientWidth.

Un contenedor mide 800 px de ancho y 300 de alto. Un hijo tiene padding-top: 10%. ¿Cuánto mide ese relleno?

  • 30 px, el 10 % del alto.
    Es lo intuitivo, pero no lo que dice CSS: los porcentajes de padding y margin, también los verticales, se calculan sobre el ancho del bloque contenedor.
  • 80 px, el 10 % del ancho.
    Correcto. Es una regla deliberada (así el relleno es igual en los cuatro lados con el mismo porcentaje) y es la base del truco de las proporciones fijas.
  • Depende de la fuente del elemento.
    Eso sería con em. Un porcentaje de padding no depende de la fuente.

Colores

CSS acepta el mismo color escrito de muchas formas. Las que vas a usar:

  • Hexadecimal: #rrggbb (cada canal de 00 a ff), su forma corta #rgb y las versiones con alfa #rrggbbaa y #rgba.
  • rgb(): canales de 0 a 255 (o en %). Con alfa: rgb(255 0 0 / 50%) (sintaxis moderna, con espacios) o rgba(255, 0, 0, 0.5) (la clásica).
  • hsl(): tono (un ángulo de 0 a 360), saturación y luminosidad. Perfecto para animar: variar solo el tono recorre el arcoíris sin cambiar el brillo.
  • Nombres (tomato) y transparent.

Lo interesante es qué te devuelve el navegador cuando lo lees. Esto es lo que dio getComputedStyle(el).color en Chrome:

Los formatos clásicos se normalizan a rgb()/rgba(), pero los espacios de color modernos conservan su notación, así que no des por hecho que siempre podrás extraer tres números con una expresión regular. (La propiedad fillStyle de un contexto 2D normaliza de otra forma: "#ff6347" para los opacos y rgba(…) para los translúcidos; y también deja oklch tal cual).

En CSS los canales van de 0 a 255; en un shader, de 0.0 a 1.0. El morado del curso, #8b7bff, es vec3(139.0, 123.0, 255.0) / 255.0 ≈ vec3(0.545, 0.482, 1.0). Es exactamente lo que hace el selector de color de los editores de GLSL antes de mandar el uniform. (Hay un matiz más, la corrección gamma: los valores de CSS están en espacio sRGB, no lineal. Lo verás en la lección 6.4).

Y no confundas el alfa de un color con opacity: el alfa afecta solo a ese color (un fondo translúcido con texto opaco encima), mientras que opacity vuelve translúcido el elemento entero con todos sus hijos… y, como acabas de ver, crea un contexto de apilamiento.

transform a fondo

transform aplica una transformación geométrica a la caja ya colocada: la mueve, la gira, la escala o la inclina al pintarla. Es la propiedad estrella de la animación web.

Las funciones

FunciónQué haceMatiz
translate(x, y), translateX(x), translateY(y)desplazalos % son del tamaño de la propia caja
rotate(ángulo)giraunidades: deg, rad, turn (90deg = 0.25turn ≈ 1.5708rad). Positivo = horario en pantalla

transform no actúa sobre las cajas inline «de texto» (un span o un a con display: inline). Lo medí: un span con rotate(45deg) siguió midiendo 44 × 18 px, y aun así getComputedStyle devolvía la matriz del giro: el navegador guarda el valor, pero no lo aplica. Con display: inline-block (o block, o siendo hijo de un flex) el mismo giro sí funciona. Los elementos reemplazados como img se transforman aunque sean inline: una img de 40 × 40 girada 45° ocupó 57 × 57.

En matemáticas (y en WebGL), un ángulo positivo gira en sentido antihorario, porque el eje Y apunta hacia arriba. En CSS y en Canvas 2D el eje Y apunta hacia abajo: la misma fórmula de rotación, con la Y invertida, se ve en sentido horario. No es que CSS gire «al revés»: es que su sistema de coordenadas está volteado. Esta inversión de Y te perseguirá por todo el curso (ratón, texturas, gl_FragCoord); en la lección 1.4 aprenderás a convertir entre los dos sistemas.

transform-origin: alrededor de qué punto

Rotar y escalar necesitan un punto fijo. Por defecto es el centro de la caja: getComputedStyle dio "50px 25px" para una caja de 100 × 50 (el 50 % 50 % ya resuelto a píxeles). Se cambia con transform-origin: 0 0 es la esquina superior izquierda, 50% 100% el centro del borde inferior (el pie de una aguja de reloj).

Síntoma: aplicas transform: rotate(…) a un <rect> o un <circle> de un SVG y, en vez de girar sobre sí mismo, describe un arco enorme o desaparece.

Causa: en los elementos SVG, el transform-origin por defecto es 0 0 del SVG, no el centro de la forma. Lo medí: getComputedStyle(rect).transformOrigin dio "0px 0px", y un rectángulo en (50, 50) girado 90° acabó en x = −70, fuera del dibujo.

Solución: transform-box: fill-box; transform-origin: center;. Con eso, el mismo rectángulo giró sobre su propio centro.

El orden importa, y se aplica de derecha a izquierda

transform admite una lista de funciones, y el orden cambia el resultado. Medí dos cajas iguales, de 100 × 50, con su centro en (250, 225):

transformmatriz que devuelve getComputedStylecentro final
translate(100px) rotate(90deg)matrix(0, 1, -1, 0, 100, 0)(350, 225): 100 px a la derecha
rotate(90deg) translate(100px)matrix(0, 1, -1, 0, 0, 100)(250, 325): ¡100 px hacia abajo!
translate(50px) scale(2)matrix(2, 0, 0, 2, 50, 0)50 px a la derecha, doble de grande
scale(2) translate(50px)matrix(2, 0, 0, 2, 100, 0)100 px: el desplazamiento también se escaló

Hay dos formas equivalentes de leerlo, y te conviene dominar las dos:

  • De derecha a izquierda, moviendo el objeto en los ejes fijos de la página. rotate(90deg) translate(100px): primero se aplica la de la derecha (la caja se desplaza 100 px a la derecha) y después la de la izquierda (todo gira 90° alrededor del origen, que es el centro original de la caja, y ese desplazamiento hacia la derecha se convierte en un desplazamiento hacia abajo).
  • De izquierda a derecha, moviendo los ejes. rotate(90deg) gira el sistema de coordenadas local de la caja; el translate(100px) siguiente avanza 100 px por el eje X ya girado, que ahora apunta hacia abajo.

La lectura de derecha a izquierda es la de las matrices. El navegador convierte cada función en una matriz (3 × 3 en 2D; por dentro usa 4 × 4, por si hay 3D) y las multiplica en el orden en que las escribiste; el punto se multiplica por la derecha, así que la función más a la derecha es la que actúa primero sobre él:

$$\texttt{transform: } A\ B\ C \quad\Longrightarrow\quad M = A \cdot B \cdot C, \qquad p' = A\,(B\,(C\,p))$$

Y matrix(a, b, c, d, e, f) es esa matriz resultante, escrita por columnas:

$$\begin{pmatrix} x' \\ y' \\ 1 \end{pmatrix} = \begin{pmatrix} a & c & e \\ b & d & f \\ 0 & 0 & 1 \end{pmatrix} \begin{pmatrix} x \\ y \\ 1 \end{pmatrix}$$

Con un giro de 90°, a = cos 90° = 0, b = sen 90° = 1, c = −sen 90° = −1, d = cos 90° = 0, y (e, f) es el desplazamiento final. En rotate(90deg) translate(100px), el desplazamiento (100, 0) queda girado: (0, 100). Son justo las matrices de la tabla. (Fíjate en que esa matriz no incluye el transform-origin: el navegador lo aplica aparte, llevando el origen al punto elegido antes de transformar y devolviéndolo después). La tercera fila, 0 0 1, y ese 1 añadido al punto son las coordenadas homogéneas, el truco que permite expresar un desplazamiento como una multiplicación; los verás a fondo en la lección 3.5. Lo que aprendas aquí con cajas lo usarás tal cual con los vértices de WebGL.

La demo: el orden, paso a paso

Una caja real con tres transformaciones. Elige el orden con el selector y mueve los deslizadores. Con «pasos intermedios» ves los fantasmas de la lectura de derecha a izquierda: el paso 1 aplica solo la última función, el paso 2 las dos últimas, y así. Los ejes rojo (X) y verde (Y) de cada caja son sus ejes locales: fíjate en que la Y apunta hacia abajo.

Tres cosas que probar: con el orden «translate rotate scale», mueve el giro y verás que la caja gira sobre sí misma, desplazada; con «rotate translate scale», el mismo giro la hace orbitar alrededor del punto de partida. Activa «comparar con el orden inverso» para ver las dos a la vez. Y cambia el origen a la esquina: la misma lista de funciones da otro resultado, porque todas giran y escalan alrededor de otro punto.

Una caja tiene transform: rotate(180deg) translate(50px, 0). ¿Hacia dónde se desplaza su centro?

  • 50 px a la derecha, porque el translate dice +50 en X.
    Eso pasaría con el orden inverso, translate(50px, 0) rotate(180deg). Aquí el desplazamiento se aplica primero (derecha a izquierda) y después se gira 180°.
  • 50 px a la izquierda.
    Sí. Leyendo de derecha a izquierda: la caja se mueve 50 px a la derecha y después todo gira 180° alrededor del centro original, así que acaba 50 px a la izquierda (y boca abajo). De izquierda a derecha: el giro de 180° invierte el eje X local y el translate avanza por ese eje invertido.
  • No se desplaza: el giro anula el desplazamiento.
    Un giro no anula un desplazamiento, lo reorienta. Para volver al sitio necesitarías un desplazamiento opuesto, no un giro.

Ejemplo 1.2.3 — Un planeta en órbita (y una luna)

Queremos un planeta que orbite alrededor del sol, y una luna que orbite alrededor del planeta. Solo con transform, actualizado en cada frame desde JavaScript.

El planeta. Está colocado en el centro del sol (left: 50%; top: 50% y márgenes negativos de medio tamaño). rotate(a) translate(110px), de derecha a izquierda: lo alejamos 110 px a la derecha y después lo giramos a radianes alrededor de su transform-origin, que es su centro inicial, es decir, el centro del sol. Resultado: una órbita de radio 110. Con el orden al revés, translate(110px) rotate(a), el planeta giraría sobre sí mismo, quieto a 110 px del sol. Pruébalo.

La luna. Es hija del planeta en el HTML, así que su transformación se aplica dentro del sistema de coordenadas ya transformado del padre: la matriz total de la luna es la del planeta multiplicada por la suya. Por eso basta con describir su órbita alrededor del planeta; la órbita alrededor del sol viene «gratis» de su padre. Esta idea, transformaciones anidadas que se multiplican de padre a hijo, es exactamente un grafo de escena, la estructura con la que se organizan las escenas 3D: la jerarquía de matrices de la lección 3.5.

Un detalle. Como el giro del planeta también gira sus ejes locales, la luna hereda ese giro. Si quisieras que el planeta no rotase sobre sí mismo (por ejemplo, para que un texto dentro se leyera siempre derecho), añadirías un giro opuesto al final: rotate(a) translate(110px) rotate(-a). Otra vez el orden: el giro de la derecha se aplica primero, alrededor del propio centro del planeta.

transform no mueve a los vecinos

La propiedad más importante de transform para animar es lo que no hace: no afecta al layout. La caja conserva su sitio en el flujo y los vecinos no se enteran. Lo medí desplazando una caja 500 px dentro de un contenedor: el offsetTop de su hermana siguió siendo 50 y su propio offsetLeft, 0. Lo que sí cambia:

  • getBoundingClientRect(), que devuelve el rectángulo alineado con los ejes que envuelve la caja transformada: la caja de 100 × 50 girada 45° dio un rectángulo de 106 × 106 (100 cos 45° + 50 sen 45° ≈ 106).
  • El área desplazable de un contenedor con overflow: auto: al desplazar la caja 500 px a la derecha, el scrollWidth del contenedor pasó de 300 a 600, y aparecieron barras de scroll. Pero hacia la izquierda no: con −500 px, el scrollWidth siguió en 300, porque lo que sale por la izquierda o por arriba no se puede alcanzar con scroll.

Como no toca el layout, el navegador puede aplicar transform (y opacity) sin recalcular la posición de nada; a menudo, incluso en otro hilo, el compositor, con la GPU. Por eso son las dos propiedades baratas de animar. La explicación completa, en la lección 2.1; la demostración de que siguen moviéndose aunque JavaScript se congele, en la 1.5.

Existen también las propiedades sueltas translate, rotate y scale (sin paréntesis: rotate: 30deg). Son cómodas para animar cada una por separado, pero tienen un orden fijo que no depende de cómo las escribas: primero translate, luego rotate, luego scale y, al final, transform. Lo comprobé: translate: 100px 0; rotate: 90deg y rotate: 90deg; translate: 100px 0 dieron el mismo resultado, con la caja desplazada a la derecha. Y cuidado: getComputedStyle(el).transform no las incluye (dice none).

Variables CSS: el puente entre JavaScript y CSS

Las propiedades personalizadas (el nombre oficial de las variables CSS) empiezan por dos guiones, se declaran en cualquier selector y se usan con var():

  1. :root es el elemento <html>. Las propiedades personalizadas se heredan, así que declaradas ahí valen para toda la página. Lo comprobé leyendo --tam en un hijo de .caja: "50px".
  2. También se pueden declarar en un elemento concreto; valen para él y sus descendientes.
  3. var() sustituye el valor como si fuera texto, y se combina con calc(): la caja midió 50 × 100 px.
  4. El segundo argumento es el respaldo, para cuando la variable no existe.
  5. Una transformación que depende de una variable: basta con cambiar la variable desde JavaScript para girar la caja.

Desde JavaScript se escriben con setProperty y se leen con getPropertyValue:

Lo comprobé: tras setProperty("--giro", "90deg"), el transform computado pasó a matrix(0, 1, -1, 0, 0, 0), mientras que la asignación con corchetes no cambió nada (solo crea una propiedad JavaScript suelta en el objeto style).

Un patrón muy limpio para animar: pasa desde JavaScript números sin unidad y pon la unidad en el CSS con calc(). Con --n: 3 y width: calc(var(--n) * 10px), el ancho fue 30 px. En JavaScript, el.style.setProperty("--progreso", 0.42), y en CSS, transform: scaleX(var(--progreso)) o rotate(calc(var(--progreso) * 1turn)). JavaScript solo calcula números; CSS decide qué significan.

Síntoma: color: var(--c, blue) no sale azul, o un width: var(--tam) hace que la caja ocupe todo el ancho de la página.

Causa: la variable existe pero su valor no tiene sentido para esa propiedad. El respaldo solo se usa cuando la variable no existe; si existe con un valor absurdo, la declaración queda «inválida en tiempo de cálculo» y la propiedad vuelve a su valor heredado o inicial, no a la regla anterior. Lo medí: con --c: 20px, el color fue el heredado del body; y con setProperty("--tam", 80) (un número sin unidad), width: var(--tam) quedó en auto y la caja midió 1000 px, todo el ancho.

Solución: pasa valores con su unidad ("80px") o multiplica en el CSS con calc(var(--tam) * 1px). Si algo «desaparece», lee la variable con getPropertyValue y comprueba que es lo que la propiedad espera.

Una transición sobre --x no anima nada: el navegador no sabe si --x es un número, una longitud o un color, así que no puede calcular valores intermedios. Lo comprobé a mitad de una transición de 1 s: opacity valía 0,4999 y --x ya valía su valor final. Para interpolar una variable hay que registrarla con @property y declarar su tipo (lección 2.2). Y un apunte de rendimiento: cambiar una variable en :root obliga a recalcular el estilo de toda la página, porque todo la hereda; cámbiala en el elemento que la usa.

overflow: lo que sobresale

overflow decide qué pasa con el contenido que no cabe en una caja:

  • visible (por defecto): sobresale y se pinta fuera.
  • hidden: se recorta. Pero la caja sigue siendo desplazable por código: con overflow: hidden, el.scrollLeft = 100 funcionó (leí 100 después).
  • clip: se recorta y no es desplazable ni por código (el mismo scrollLeft = 100 se quedó en 0).
  • scroll y auto: barras de scroll siempre o solo cuando hace falta.

Cualquier valor distinto de visible (salvo clip) crea además un contexto de formato de bloque, y por eso overflow: hidden es uno de los remedios para los márgenes que se fusionan.

Que overflow: hidden se pueda desplazar por código es la base de muchos carruseles y efectos de «revelado»: el usuario no ve barras ni puede arrastrar, pero tu JavaScript mueve el contenido con scrollLeft o scrollTo({ left, behavior: "smooth" }). Si quieres recortar sin que nada pueda desplazar la caja (ni siquiera el navegador al enfocar un elemento de dentro), usa overflow: clip.

Ejercicios

Ejercicio 1.2.1 — Tres columnas que no caben

Las tres columnas deberían caber en una fila (cada una ocupa un tercio), pero la tercera baja a la siguiente línea. Arréglalo añadiendo una sola declaración al CSS, sin tocar anchos, rellenos ni bordes. Al terminar, la consola debe decir que la suma de los offsetWidth no supera el ancho de la fila y que las tres columnas tienen el mismo offsetTop.

Pista 1

Calcula el offsetWidth de una columna a mano: un tercio de 600 más el relleno y el borde de los dos lados. ¿Caben tres?

Pista 2

¿Qué propiedad hace que width incluya el relleno y el borde?

Solución explicada

Con content-box, cada columna ocupa 200 + 2·10 + 2·2 = 224 px, y tres suman 672: más que los 600 de la fila, así que la tercera salta de línea. box-sizing: border-box hace que los 200 px incluyan relleno y borde: cada columna ocupa exactamente 200 (el contenido encoge a 176) y las tres suman 600.

Fíjate en un detalle: en el HTML las tres columnas van pegadas, </div><div>, sin espacios entre ellas. No es casualidad: son inline-block, y cualquier salto de línea entre ellas sería un nodo de texto que se pintaría como un espacio de unos 4 px, suficiente para que 600 + 8 ya no cupiera. Prueba a separarlas en líneas distintas en la pestaña HTML. (En una maqueta real usarías display: flex, que ignora esos espacios).

Ejercicio 1.2.2 — La aguja del reloj

La aguja de los segundos debería girar alrededor de su pie, en el centro de la esfera, como en un reloj de verdad. Ahora gira alrededor de su propio centro. Arréglalo con CSS. Al terminar, la base de la aguja debe quedarse quieta en el centro mientras la punta recorre la esfera.

Pista 1

¿Alrededor de qué punto gira por defecto un elemento HTML? ¿Dónde está, en coordenadas de la aguja, el punto que debería quedarse quieto?

Pista 2

transform-origin acepta porcentajes de la propia caja: 0 0 es la esquina superior izquierda y 100% 100% la inferior derecha.

Solución explicada

transform-origin: 50% 100% pone el punto fijo en el centro del borde inferior de la aguja, que es justo el centro de la esfera (la aguja va de y = 20 a y = 100 y está centrada en x). Por defecto el origen es 50% 50%, el centro de la aguja, y por eso giraba como una hélice.

Por dentro, un transform-origin equivale a trasladar el origen al punto elegido, aplicar la transformación y deshacer la traslación: translate(o) rotate(θ) translate(−o). Leído de derecha a izquierda: llevar el pie al origen, girar, devolverlo a su sitio. Es exactamente la receta que usarás con matrices para «girar alrededor de un punto» en la lección 3.5.

Ejercicio 1.2.3 — Un foco que sigue al ratón

El CSS ya dibuja un foco de luz centrado en las variables --x y --y (en píxeles, relativas a la escena). Escribe el JavaScript que las actualiza al mover el puntero por la escena, para que el foco lo siga. Además, haz que el radio del foco (--radio) sea mayor mientras mantienes pulsado el botón. Imprime en la consola las coordenadas de cada pointerdown.

Pista 1

e.clientX es la posición del puntero en la ventana; escena.getBoundingClientRect().left es dónde empieza la escena en la ventana. La resta es la posición dentro de la escena. (Los sistemas de coordenadas del puntero, a fondo, en la lección 1.4).

Pista 2

escena.style.setProperty("--x", valor + "px"). ¿Por qué --x necesita la unidad y --radio no? Mira cómo usa cada una el CSS.

Solución explicada

En cada pointermove calculamos la posición relativa a la escena restando la esquina de su rectángulo, y la escribimos en --x/--y con setProperty. El navegador recalcula el radial-gradient con los nuevos valores: JavaScript solo mueve dos números y CSS pinta.

La diferencia de unidades es el punto fino. --x se usa directamente como posición (circle at var(--x) var(--y)), así que tiene que ser una longitud válida: "123px". --radio se usa dentro de calc(var(--radio) * 1px), así que debe ser un número sin unidad; si le pasaras "160px", el calc quedaría 160px * 1px, que es inválido (no se pueden multiplicar dos longitudes), y el degradado entero dejaría de pintarse, como en el bestiario de la variable inválida.

Un fleco que dejamos suelto: si sueltas el botón fuera de la escena, el pointerup no llega a ella y el foco se queda grande. Se arregla con la captura de puntero (setPointerCapture), que verás en la lección 1.4.

Este patrón, «el puntero escribe variables CSS», es el mismo que usarás para pasar u_mouse a un shader en la lección 7.2: allí el destino es un uniform en lugar de una variable CSS.

Ejercicio 1.2.4 — z-index: 9999 y sigue debajo

Al pasar el ratón por la primera tarjeta, esta sube un poco y muestra un aviso (amarillo) que debería quedar por encima de la segunda tarjeta; pero queda debajo, a pesar de su z-index: 9999. Arréglalo sin cambiar el HTML ni el z-index del aviso. Para comprobarlo sin ratón, el aviso está siempre visible y el JavaScript mira qué elemento hay en un punto de la zona de solape dos veces: en reposo y simulando el :hover de la tarjeta 1 con la clase hover. Al terminar, las dos líneas de la consola deben decir aviso.

Pista 1

Dibuja el árbol de contextos de apilamiento: ¿qué elementos crean uno, en reposo y con :hover? ¿Contra quién compite el z-index: 9999 del aviso?

Pista 2

Las dos tarjetas tienen position: relative y z-index: 1. Con el mismo z-index, ¿cuál se pinta encima, la primera o la segunda?

Pista 3

Si quitas el z-index: 1, la línea «en reposo» se arregla, pero la del :hover no. ¿Qué propiedad tiene la tarjeta cuando está en :hover, y qué crea esa propiedad?

Solución explicada

Por qué falla. Cada tarjeta, con position: relative y z-index: 1, crea su propio contexto de apilamiento. El aviso vive dentro del de la tarjeta 1, así que su 9999 solo le sirve frente a otros hijos de la tarjeta 1. Hacia fuera compiten las dos tarjetas con el mismo z-index, y el empate lo gana la que va después en el HTML: la tarjeta 2 se pinta encima de la tarjeta 1… con el aviso dentro.

Medio arreglo. Quitar el z-index: 1 arregla el reposo: las tarjetas ya no crean contexto y el aviso compite en el contexto raíz, donde su 9999 gana a todo. Pero con :hover, la tarjeta 1 tiene transform, y transform crea un contexto de apilamiento: el aviso vuelve a quedar encerrado, y la tarjeta 2 (posicionada y posterior en el HTML) vuelve a pintarse encima. Es la trampa de la caja de senior «Animar transform puede cambiar quién está encima».

Arreglo completo. Sin z-index en reposo, y z-index: 2 en el :hover: cuando la tarjeta crea su contexto, ese contexto queda por encima de la tarjeta vecina. Otra solución que pasa las dos comprobaciones es .t1 { z-index: 2; }, que sube el grupo entero de la tarjeta 1; pero en una lista de muchas tarjetas tendrías que decidir de antemano cuál va encima, mientras que la regla del :hover sube siempre la que tiene el ratón.

  • La cascada decide qué regla gana: importancia, especificidad (ids, clases, tipos; se comparan columna a columna) y orden. getComputedStyle te da el valor que ganó, ya resuelto.
  • La caja tiene contenido, padding, borde y margen. Con content-box, width es solo el contenido; con border-box, llega hasta el borde. offsetWidth y clientWidth hablan del layout e ignoran transform; getBoundingClientRect() dice dónde se ve la caja, con transformaciones.
  • Los márgenes verticales se fusionan, también entre padre e hijo (remedio: display: flow-root). inline ignora width/height; el canvas es inline por defecto (franja inferior: display: block) y en un flex necesita min-width: 0.
  • absolute se coloca respecto al ancestro posicionado más cercano; transform y filter también crean bloque contenedor, incluso para los fixed.
  • z-index solo funciona en elementos posicionados (o hijos de flex/grid) y solo compite dentro de su contexto de apilamiento; opacity, transform y filter crean contextos.
  • Un px CSS no es un píxel físico: devicePixelRatio. Los % de padding son del ancho del contenedor; los de translate(), de la propia caja.
  • transform: la lista se aplica de derecha a izquierda sobre la caja (M = A·B·C), alrededor de transform-origin (en SVG, 0 0). No afecta al layout: por eso es barata de animar.
  • Las variables CSS se heredan, se escriben con setProperty y no se interpolan sin @property. El respaldo solo actúa si la variable no existe.
