Datos binarios: ArrayBuffer y TypedArrays

La GPU no entiende arrays ni objetos de JavaScript: consume bytes crudos, en un formato exacto. Aquí aprendes a fabricar esos bytes: el ArrayBuffer, las vistas tipadas que lo interpretan, DataView y el orden de los bytes, la precisión real de un float de 32 bits y cómo empaquetar vértices entrelazados para un VBO.

⏱ 85 minRequisitos: 1.3

Al terminar esta lección

  • Sabrás por qué WebGL necesita bytes y qué pasa si le das un array normal.
  • Crearás ArrayBuffers y vistas tipadas, y entenderás que varias vistas pueden compartir la misma memoria, con byteOffset, byteLength y la regla de alineación.
  • Leerás y escribirás con DataView controlando el orden de los bytes, sin caer en su valor por defecto.
  • Predecirás la precisión de un float32 (Math.fround) y qué hacen los enteros al desbordar (Uint8Array frente a Uint8ClampedArray).
  • Distinguirás subarray (vista) de slice (copia) y copiarás en bloque con set.
  • Construirás un buffer de vértices entrelazados y calcularás el stride y los offsets que pedirá gl.vertexAttribPointer.

Por qué bytes

En el esquema de la lección 0.1, el canal principal entre JavaScript y la GPU son los buffers: bloques de memoria que la GPU lee directamente, sin saber nada de JavaScript. Para la GPU, un buffer de vértices es una tira de bytes; tú le dices después «cada 12 bytes empieza un vértice; los 8 primeros son dos floats de 32 bits; los 4 siguientes, cuatro bytes de color». Si los bytes no están exactamente así, dibuja basura, o nada. (Fíjate en la ortografía: en este curso escribimos buffer, como las APIs, para estos bloques de bytes, y búfer para la rejilla de píxeles en la que dibuja un canvas, el de la lección 1.1. Son cosas distintas.)

Un array de JavaScript no es una tira de bytes. [0.5, 1, 1.5] es una lista de valores de JavaScript, cada uno un double de 64 bits, que el motor guarda como le conviene (a veces como enteros pequeños marcados, a veces como punteros a objetos en otro sitio de la memoria). No hay forma de entregárselo a la GPU tal cual. Por eso existen los TypedArrays: arrays de números de un tipo fijo (float de 32 bits, entero sin signo de 8…) guardados uno detrás de otro, sin huecos, en un bloque de memoria contigua.

Lo peor es que, si te equivocas, WebGL no siempre se queja. Lo comprobé:

Le paso a gl.bufferData(gl.ARRAY_BUFFER, datos, …)Resultado
new Float32Array([0.5, 1, 1.5])un buffer de 12 bytes (3 × 4). Correcto.
[0.5, 1, 1.5], un array normalsin excepción y sin error de GL… y un buffer de 0 bytes
new Float64Array([0.5, 1, 1.5])un buffer de 24 bytes de doubles; si el atributo dice gl.FLOAT, la GPU los lee como floats: (0.5, 1) se convierte en (0, 1.75, 0, 1.875)

El caso del array normal merece explicación: bufferData tiene otra forma, bufferData(target, tamañoEnBytes, uso), que reserva un buffer vacío de ese tamaño. Como un array no es un bloque de bytes, WebIDL (la capa que convierte los argumentos de JavaScript para las APIs del navegador) intenta convertirlo en un número: Number([0.5, 1, 1.5]) es NaN, que como tamaño vale 0.

Síntoma: tu geometría no aparece; la consola está limpia y gl.getError() devuelve 0.

Causa: le pasaste a gl.bufferData un array normal de JavaScript. Se interpretó como un tamaño (0 bytes), así que el buffer está vacío y no hay vértices que dibujar. Si lo que pasaste fue un Float64Array, el buffer tiene datos, pero de 8 bytes por número, y la GPU los lee como floats de 4: basura.

Solución: new Float32Array(tusNumeros) para vértices, Uint16Array o Uint32Array para índices, Uint8Array para píxeles. Compruébalo con gl.getBufferParameter(gl.ARRAY_BUFFER, gl.BUFFER_SIZE): debe valer el número de elementos por los bytes de cada uno.

Los datos binarios aparecen en todo lo que conecta con la GPU: vértices e índices (lección 5.3), texturas (Uint8Array de píxeles RGBA, lección 5.5), gl.readPixels, los píxeles de un canvas 2D (ImageData), y también fuera de ella: audio, archivos de modelos 3D, WebSockets binarios. La GPU de juguete de la lección 4.3 y los VBO de la 4.4 parten de aquí.

ArrayBuffer: un bloque de bytes

new ArrayBuffer(16) reserva 16 bytes contiguos, todos a cero. Eso es todo: un ArrayBuffer no tiene índices ni sabe qué significan sus bytes. Su tamaño (byteLength) es fijo al crearlo (hay una variante redimensionable, new ArrayBuffer(4, { maxByteLength: 16 }), que no necesitarás casi nunca). Para leer o escribir hay que mirarlo a través de una vista: un TypedArray o un DataView.

Las vistas tipadas

Cada TypedArray interpreta los bytes como números de un tipo concreto. Estos son los que usarás; la columna de bytes es su BYTES_PER_ELEMENT, comprobado:

TipoBytesRangoEn gráficos
Float32Array4float de 32 bits (~7 cifras)posiciones, normales, UV, uniforms, matrices
Float64Array8double, como los números de JScálculos en CPU; la GPU casi nunca
Uint8Array10 … 255, da la vuelta al desbordarpíxeles, colores empaquetados, bytes crudos
Uint8ClampedArray10 … 255, se saturaImageData.data del canvas 2D

Uint16Array / Int16Array20 … 65 535 / −32 768 … 32 767índices de mallas
Uint32Array / Int32Array40 … 4 294 967 295 / ±2 147 483 648índices grandes, datos enteros

Se crean de tres formas: con una longitud (new Float32Array(3) da tres ceros), a partir de números (new Float32Array([1, 2, 3]), que los convierte uno a uno) o sobre un buffer existente (new Float32Array(buffer, byteOffset, longitud)). Se parecen a un array, pero con diferencias importantes, todas comprobadas:

  • Longitud fija: no hay push (TypeError: a.push is not a function). Escribir fuera de rango no da error: se ignora (a[10] = 5 en un array de 3 no hizo nada, y leer a[10] dio undefined).
  • Cada escritura se convierte al tipo: en un Float32Array, "3.5" se guarda como 3.5, null como 0, undefined como NaN. En los enteros, lo veremos enseguida, pasan cosas más raras.
  • map devuelve el mismo tipo: new Uint8Array([100, 200]).map((x) => x * 1.5) dio [150, 44], porque 300 no cabe en un byte. Si quieres un array normal, Array.from(tipado).
  • JSON.stringify(new Float32Array([1.5, 2])) da '{"0":1.5,"1":2}', un objeto: conviértelo antes con Array.from.

Varias vistas, una memoria

Lo más potente de las vistas es que varias pueden mirar el mismo buffer. Escribir por una cambia lo que ven las demás:

  1. Cuatro bytes, a cero.
  2. Dos vistas del mismo buffer: una ve un float de 32 bits; la otra, cuatro bytes sueltos. No se copia nada: las dos leen y escriben la misma memoria.
  3. Escribimos 1.0 como float y miramos sus bytes: 0, 0, 128, 63, es decir, 00 00 80 3F en hexadecimal. El float 1.0 en binario es 0x3F800000, pero en memoria aparece al revés, empezando por el byte menos significativo. Es el orden little-endian; lo explicamos en la sección de DataView.
  4. Cambiamos solo el último byte (el más significativo) de 0x3F a 0x40: los bits son ahora 0x40800000, que como float vale 4. Lo comprobé en Chrome. Tocando bytes cambiamos el exponente del float: así de literal es la memoria compartida.

byteOffset, byteLength y la regla de alineación

Una vista puede empezar en cualquier punto del buffer y abarcar solo una parte. En la figura, un buffer de 16 bytes con tres vistas a la vez:

La vista parcial la comprobé con new Float32Array(buffer, 4, 2): byteOffset 4, byteLength 8 y length 2. Y aquí aparece la regla que más muerde: una vista de elementos de N bytes tiene que empezar en un byteOffset múltiplo de N (y, si no das longitud, el resto del buffer tiene que ser múltiplo de N). Los errores exactos de Chrome:

CódigoError
new Float32Array(new ArrayBuffer(16), 2)RangeError: start offset of Float32Array should be a multiple of 4
new Float32Array(new ArrayBuffer(10))RangeError: byte length of Float32Array should be a multiple of 4
new Float32Array(new ArrayBuffer(16), 4, 4)RangeError: Invalid typed array length: 4 (4 + 4·4 = 20 > 16)

¿Por qué la restricción? Una vista calcula la dirección de cada elemento como byteOffset + i × 4 y lo lee con una sola instrucción de la CPU, que es rápida (y en algunos procesadores, solo posible) cuando la dirección es múltiplo del tamaño. Los Uint8Array pueden empezar donde quieran (new Uint8Array(buffer, 3) funcionó), y DataView no tiene esta restricción: leyó sin problema un float en el byte 2.

Síntoma: al crear una vista sobre un buffer que contiene datos mezclados (una cabecera de 2 bytes, colores de 3 bytes…), salta este RangeError.

Causa: una vista de floats (o de enteros de 2 o 4 bytes) solo puede empezar en un byte múltiplo de su tamaño.

Solución: diseña el formato con relleno (padding) para que cada campo quede alineado (por ejemplo, un color de 3 bytes seguido de 1 byte de relleno), lee los campos desalineados con DataView, o copia el trozo a un buffer nuevo con slice. Es la misma razón por la que los formatos de vértices y los bloques de uniforms de la GPU tienen reglas de alineación.

Tienes const f = new Float32Array(2) y const b = new Uint8Array(f.buffer). Ejecutas f[1] = 1.0. ¿Qué contiene b?

  • [0, 0, 0, 0, 63, 128, 0, 0]
    Los bytes están al revés: en memoria, un float se guarda empezando por su byte menos significativo (little-endian), así que el 0x3F va el último.
  • [0, 0, 0, 0, 0, 0, 128, 63]
    Correcto. f[1] ocupa los bytes 4 a 7. El float 1.0 es 0x3F800000, y en orden little-endian sus bytes son 00 00 80 3F (128 = 0x80, 63 = 0x3F).
  • [0, 1]
    Eso sería si la vista de bytes convirtiera los valores. No convierte nada: muestra los bytes crudos del buffer, que son 8 (dos floats de 4 bytes).

DataView y el orden de los bytes

Un número de varios bytes se puede guardar empezando por el byte más significativo (big-endian, como escribimos los números: 3F 80 00 00) o por el menos significativo (little-endian: 00 00 80 3F). Casi todo el hardware actual (x86, ARM de móviles y Macs, y las GPUs) es little-endian. Los TypedArrays usan el orden de la plataforma: lo comprobé con new Uint8Array(new Uint16Array([1]).buffer), que dio [1, 0]. Como WebGL también usa el orden de la plataforma, un Float32Array pasa a la GPU tal cual y todo encaja.

DataView es la otra forma de mirar un buffer: sin tipo fijo, con métodos para leer y escribir cualquier tipo en cualquier byte, y con el orden explícito: dv.getFloat32(byteOffset, littleEndian), dv.setUint16(byteOffset, valor, littleEndian)… Aquí está la trampa: si no pasas el tercer argumento, DataView usa big-endian. Lo comprobé:

  • dv.setFloat32(0, 1.0) escribió [63, 128, 0, 0]; con setFloat32(0, 1.0, true), [0, 0, 128, 63], como un Float32Array.
  • Leer los bytes de un Float32Array que contiene 1.0 con getFloat32(0) dio 4.600602988224807e-41: los mismos cuatro bytes, leídos al revés, son un número diminuto y absurdo. Con getFloat32(0, true), 1.

Síntoma: lees con DataView unos datos que escribiste con un TypedArray (o que vienen de un archivo) y obtienes valores diminutos, enormes o multiplicados por 256.

Causa: DataView usa big-endian si no le dices otra cosa, y los TypedArrays (y casi todos los formatos modernos) usan little-endian. Con los bytes [1, 0], getUint16(0) dio 256.

Solución: pasa siempre true como último argumento (getFloat32(o, true), setUint32(o, v, true)) salvo que el formato sea big-endian de verdad (algunos formatos de red y de archivo antiguos lo son).

La demo: de números a bytes, y de bytes a bits

Escribe números, elige el tipo y mira cómo quedan en memoria. Los valores que cambian al guardarse (porque no caben o pierden precisión) salen marcados. Pulsa un valor o uno de sus bytes para ver sus bits: en un float, el signo, el exponente y la mantisa, con la cuenta que reconstruye el valor.

Prueba esto: 0.1 en Float32Array frente a Float64Array (mira cuántos bits de mantisa tiene cada uno); 16777217 en float32 (se convierte en 16777216: ya no hay bits para la última unidad); 300 y −1 en Uint8Array frente a Uint8ClampedArray; −1 en Int16Array (todos los bits a 1: el complemento a dos); y cambia el orden de bytes a big-endian para ver los mismos números como los escribiría DataView sin su tercer argumento.

La precisión real de un float32

La GPU trabaja casi siempre con floats de 32 bits: vértices, uniforms, casi todos los cálculos de los shaders. Un float32 tiene 1 bit de signo, 8 de exponente y 23 de mantisa, y su valor es

$$\text{valor} = (-1)^{s} \times 1.m \times 2^{\,e - 127}$$

donde 1.m es un número entre 1 y 2 (el 1 inicial no se guarda: está implícito) y el exponente se guarda sumándole 127 para no necesitar signo. Los patrones de bits que obtuve en Chrome:

Valorsigno · exponente · mantisahex
1.00 · 01111111 · 000…0 (e = 127 → 20)0x3F800000
0.50 · 01111110 · 000…0 (2−1)0x3F000000
−2.51 · 10000000 · 0100…0 (1,25 × 21)0xC0200000
0.10 · 01111011 · 100110011001100110011010x3DCCCCCD
−01 · 00000000 · 000…0 (solo el signo)0x80000000
Infinity / NaNexponente 11111111, mantisa 0 / distinta de 00x7F800000 / 0x7FC00000

0.1 es una fracción periódica en binario (0,000110011001100…), así que hay que cortarla en 23 bits y redondear. Math.fround(x) te dice qué número queda al guardar x en un float32: Math.fround(0.1) es 0.10000000149011612, y es exactamente lo que devuelve new Float32Array([0.1])[0]. Tres consecuencias medidas:

  • Unas 7 cifras decimales, frente a las 15–17 de un double.
  • Enteros exactos hasta 224 = 16 777 216. A partir de ahí faltan números: new Float32Array([16777217]) guardó 16 777 216, y 16 777 219 se convirtió en 16 777 220 (solo quedan los pares).
  • Rango: hasta unos 3,4 · 1038 (Math.fround(1e39) dio Infinity), y los más pequeños rondan 1,4 · 10−45.

El uniform u_time que usan los shaders de este curso es un float32. Al principio sobra precisión, pero cuanto más grande es el número, más separados están los floats consecutivos: Math.fround(10000.016) ya es 10000,015625, y Math.fround(100000.016) (unas 27 horas en segundos) es 100000,015625. Con saltos de casi 8 ms entre valores representables, una animación que lleva un día en marcha empieza a moverse a trompicones o a dar pasos visibles. Por eso se reinicia el tiempo, se pasa en trozos o se envuelve con un módulo antes de mandarlo. Lo verás con detalle en la lección 3.7.

Una curiosidad: Math.fround(Math.fround(0.1) + Math.fround(0.2)) es 0,30000001192092896, que es exactamente Math.fround(0.3). En float32, el famoso 0.1 + 0.2 «sale bien»: los errores de redondeo se compensan de otra forma que en double. No es que float32 sea más preciso; es otra forma de equivocarse. Y existe también un tipo aún más pequeño: Chrome ya incluye Float16Array (floats de 16 bits, los de las texturas HALF_FLOAT), donde 0.1 se guarda como 0,0999755859375, los enteros solo son exactos hasta 2048 y 70 000 ya es Infinity.

Ejemplo 1.6.1 — Desmontar un float con operaciones de bits

La demo te enseña los bits; ahora los sacamos nosotros, con una vista Uint32Array sobre el mismo buffer de un Float32Array y los operadores de bits de la lección 1.3. Después reconstruimos el valor con la fórmula y comprobamos que sale exactamente el float guardado.

La vista entera. u mira los 4 bytes de f como un Uint32. Al escribir en f[0], u[0] pasa a contener los bits del float, sin conversión: es el mismo truco de aliasing de antes, y lo que en GLSL hace la función floatBitsToUint. Como ambas vistas usan el orden de la plataforma, el entero sale con el bit de signo arriba, sin preocuparnos del little-endian.

Los campos. bits >>> 31 baja el bit 31 a la posición 0 (con >>>, que rellena con ceros, y no >>, que copiaría el signo). (bits >>> 23) & 0xFF baja el exponente y se queda con sus 8 bits. bits & 0x7FFFFF se queda con los 23 bits de la mantisa (0x7FFFFF son 23 unos).

La reconstrucción. Con la fórmula, todos los valores salen idénticos al float guardado (la comprobación usa ===). Fíjate en dos líneas: 0.1 da 0x3DCCCCCD con exponente 123 (2−4) y se reconstruye como 0,10000000149011612, no como 0,1, porque lo que desmontamos es lo que se guardó; y 16777217 se reconstruye como 16777216, porque con 23 bits de mantisa y exponente 24 ya no queda un bit para la última unidad. (La fórmula de la reconstrucción no vale para 0, los subnormales, Infinity ni NaN, que usan los exponentes 0 y 255 como casos especiales.)

Enteros que desbordan… o se saturan

Al escribir un número en una vista entera, primero se trunca hacia cero y después se reduce al rango del tipo. Lo que pasa con los que no caben depende del tipo:

Los tipos normales hacen aritmética modular: el valor da la vuelta (u8[0] = 255; u8[0]++ dejó un 0). Uint8ClampedArray satura: lo que pasa de 255 se queda en 255 y lo negativo en 0, y además redondea en lugar de truncar, con una regla peculiar: los medios van al par más cercano (1,5 → 2, 2,5 → 2, 3,5 → 4, 254,5 → 254; lo comprobé). Es el tipo de ImageData.data, los píxeles de un canvas 2D (lección 2.6), precisamente para que aclarar u oscurecer una imagen no produzca píxeles absurdos.

Síntoma: subes el brillo o sumas dos imágenes y justo las zonas más claras aparecen negras o de colores extraños.

Causa: los píxeles están en un Uint8Array (o en tu propio array de bytes), y los valores de más de 255 dan la vuelta: 250 + 80 = 330 se guarda como 74.

Solución: usa Uint8ClampedArray, que satura en 255, o limita tú el valor: Math.min(255, v). En un shader no pasa: allí los colores son floats de 0 a 1 y la GPU recorta al escribir en un framebuffer de 8 bits.

¿Qué valen new Uint8Array([260, -2]) y new Uint8ClampedArray([260, -2])?

  • [255, 0] y [255, 0]
    Solo la versión clamped satura. Un Uint8Array normal hace aritmética modular: el valor da la vuelta.
  • [4, 254] y [255, 0]
    Correcto. En Uint8Array, 260 − 256 = 4 y −2 + 256 = 254 (módulo 256). Uint8ClampedArray recorta al rango: 255 y 0.
  • [4, 254] y [4, 254]
    Uint8ClampedArray existe justo para no dar la vuelta: satura en los extremos.

subarray, slice y set

Parecen iguales y son opuestos:

  • a.subarray(1, 3) crea una vista nueva sobre el mismo buffer: no copia nada. Comprobado: al escribir 99 en el primer elemento de la subvista, cambió a[1]; y la subvista tenía byteOffset 4 y el mismo buffer que a.
  • a.slice(1, 3) crea una copia con su propio buffer: modificarla no afecta a a.

destino.set(origen, desplazamiento) copia un array (o un TypedArray) entero dentro de otro, a partir de una posición: new Float32Array(6) con set([1, 2, 3], 2) quedó [0, 0, 1, 2, 3, 0]. Es la forma rápida de montar un buffer a trozos, mucho más que un bucle elemento a elemento. Maneja bien el solapamiento (copiar una parte de un array sobre sí mismo desplazada funcionó como si hubiera copia intermedia), y si no cabe lanza RangeError: offset is out of bounds. Con subarray y set manipulas trozos de un buffer grande sin crear memoria nueva, que es justo lo que querrás hacer en un bucle de animación (lección 1.3: nada de basura en los bucles calientes).

Transferir en vez de copiar

Para mandar un buffer a un Web Worker (lección 1.5) sin copiar sus megas, se transfiere: worker.postMessage(buffer, [buffer]). Tras transferirlo, el buffer original queda vacío y desconectado (detached). Lo comprobé con structuredClone(buffer, { transfer: [buffer] }) y con buffer.transfer(): el original pasó a byteLength 0 (buffer.detached === true), y una vista que había sobre él pasó a tener length 0.

Adelanto del VBO: vértices entrelazados

Un triángulo con color por vértice tiene, para cada uno de sus tres vértices, una posición (x, y) y un color (r, g, b). Se pueden guardar en dos buffers separados, o entrelazados en uno solo: todos los datos del vértice 0, luego todos los del vértice 1, etc. El entrelazado es muy común porque la GPU lee cada vértice de una zona contigua de memoria.

Dos números describen el formato: el stride, cuántos bytes hay de un vértice al siguiente, y el offset de cada atributo, en qué byte del vértice empieza. Son exactamente dos de los argumentos de gl.vertexAttribPointer(loc, tamaño, tipo, normalizado, stride, offset), que desmontarás llamada a llamada en la lección 5.3. Para el formato de todo floats:

Comprobé los dos formatos dibujando de verdad un triángulo con WebGL2 (rojo, verde y azul en sus vértices) y leyendo los píxeles resultantes con gl.readPixels: los dos dieron exactamente los mismos colores (el píxel de la esquina roja, (254, 1, 1)) y ningún error de GL. El compacto ocupa 12 bytes por vértice en lugar de 20: con un millón de vértices, 8 MB menos que subir a la GPU.

Ejemplo 1.6.2 — Empaquetar el triángulo en los dos formatos

Partimos de los vértices como objetos, que es como los escribirías a mano, y construimos los dos buffers. Después comprobamos byte a byte que cada dato está donde dicen el stride y el offset.

Formato 1. Todo son floats, así que basta un Float32Array. La única cuenta delicada es la de los índices: el vértice i empieza en el float i × 5 (índice de la vista), que es el byte i × 20 (el stride). Confundir índices de elementos con bytes es el error clásico de este código. set copia los cinco valores de golpe. Los colores se dividen por 255 porque en este formato van como floats de 0 a 1, como los usará el shader.

Formato 2. Un ArrayBuffer de 36 bytes y dos vistas sobre él. Las posiciones se escriben con la vista de floats: el vértice i empieza en el byte i × 12, que en índices de float es i × 12 / 4 = i × 3. Funciona porque 12 es múltiplo de 4, de modo que todas las posiciones quedan alineadas (con un stride de 11 no podrías usar un Float32Array para las posiciones: necesitarías DataView). Los colores van en bytes, en la vista Uint8Array, a partir del byte 8 de cada vértice, sin dividir: la GPU los normalizará si se lo pides con normalized = true.

La comprobación. Leemos el vértice 1 con DataView exactamente como lo hará la GPU: floats en los bytes 12 y 16, colores en los bytes 20 a 23. Los bytes crudos del vértice muestran los dos floats en little-endian (0.8 es 0x3F4CCCCD, en memoria 205 204 76 63) seguidos de los cuatro bytes de color.

Cada vértice tiene posición (x, y, z) y coordenadas de textura (u, v), todo en float32 y entrelazado. ¿Qué stride y qué offset tiene el atributo de UV?

  • stride 5, offset 3
    Son las cuentas en floats. vertexAttribPointer quiere bytes: cada float son 4.
  • stride 20, offset 12
    Correcto: 5 floats × 4 bytes = 20 bytes por vértice, y las UV empiezan después de x, y, z: 3 × 4 = 12 bytes.
  • stride 8, offset 12
    8 bytes es el tamaño del atributo UV (2 floats), no el stride. El stride es el tamaño del vértice completo.

El formato entrelazado es un array de estructuras (AoS): todos los datos de un vértice juntos. La alternativa es una estructura de arrays (SoA): un buffer con todas las posiciones y otro con todos los colores. Para la GPU los dos funcionan. En CPU, el SoA suele ser mejor para simular miles de partículas: guardar xs, ys, vxs, vys en cuatro Float32Array y recorrerlos en un bucle evita crear un objeto por partícula (sin basura para el recolector, lección 1.3) y aprovecha mejor la caché del procesador. Lo usarás en el proyecto de la lección 2.8 y en las partículas en GPU de la 7.5.

b.toString(16) da el hexadecimal de un número; .padStart(2, "0") añade el cero delante de los bytes menores que 16.

Pista 2

La tercera prueba usa una subarray: su buffer es el de f entero. Si haces new Uint8Array(tipado.buffer), verás los 12 bytes. ¿Qué dos propiedades de la vista te dicen dónde empieza y cuánto ocupa?

Solución explicada

La clave está en la tercera prueba. f.subarray(1, 2) es una vista del mismo buffer de 12 bytes, que empieza en el byte 4 y ocupa 4. Una vista de bytes hecha con new Uint8Array(tipado.buffer) vería el buffer entero; hay que pasarle tipado.byteOffset y tipado.byteLength para mirar solo la parte que corresponde. Es un error muy común al convertir trozos de buffers.

Los bytes de 1.0 salen 00 00 80 3F porque la memoria es little-endian; los de −2, 00 00 00 C0 (−2 es 0xC0000000: signo 1, exponente 128). En bigEndian, setFloat32 sin tercer argumento escribe cada float con su byte más significativo primero, que es el orden en que se escribe el número en hexadecimal: 3F 80 00 00.

Ejercicio 1.6.2 — Más brillo sin desbordar

La función aclarar suma 90 a los canales rojo, verde y azul de cada píxel de un degradado. Arriba ves el original; abajo, el resultado: la parte clara se ha vuelto oscura. Arréglalo para que los valores que se pasen de 255 se queden en 255 (sin tocar el canal alfa). La consola comprueba tres píxeles.

Pista 1

¿Qué hace un Uint8Array cuando le sumas 90 a un 200? ¿Qué tipo de TypedArray no da la vuelta?

Pista 2

imagen.data ya es un Uint8ClampedArray. El problema es la copia.

Solución explicada

new Uint8Array(imagen.data) copia los bytes a un array de enteros normal, que hace aritmética módulo 256: un píxel de 200 + 90 = 290 se guarda como 34, y la zona clara del degradado se vuelve oscura (la consola lo muestra para x = 250). Copiando a un Uint8ClampedArray, el mismo += satura en 255: la zona clara se queda blanca, que es lo que se espera de «más brillo». Además, ahora el array ya es del tipo que pide ImageData y no hace falta la conversión final.

Otra solución válida es mantener el tipo y limitar a mano: px[i] = Math.min(255, px[i] + cantidad). Y un detalle del Uint8ClampedArray: si la cantidad fuera decimal (por ejemplo 90,5), redondearía los medios al par más cercano en lugar de truncar.

Una línea del código de partida que no es el problema: { willReadFrequently: true } al pedir el contexto le avisa a Chrome de que vas a leer píxeles con getImageData; así guarda el canvas en memoria de la CPU y cada lectura no tiene que traerlo desde la GPU.

Ejercicio 1.6.3 — Empaqueta los vértices para la GPU

El código de abajo ya sabe dibujar un triángulo con WebGL2 (ese código lo desmontarás en la lección 5.2; aquí no lo toques). Solo le falta el buffer: completa empaquetar para que devuelva un Float32Array entrelazado con x, y, r, g, b por vértice (colores de 0 a 1), y pon los valores correctos de STRIDE y OFFSET_COLOR en bytes. Si lo haces bien, verás un triángulo con un degradado rojo, verde y azul, y la consola mostrará el tamaño del buffer en bytes.

Pista 1

¿Cuántos floats tiene cada vértice? ¿Cuántos bytes ocupa cada float?

Pista 2

El vértice i empieza en el índice i × 5 del Float32Array, pero en el byte i × 20. STRIDE y OFFSET_COLOR van en bytes; los índices del array, en floats.

Solución explicada

Cada vértice son 5 floats (x, y, r, g, b) de 4 bytes: STRIDE = 20. El color empieza después de x e y: OFFSET_COLOR = 8. empaquetar crea un Float32Array de 3 × 5 = 15 floats (60 bytes) y copia cada vértice con set en el índice i × 5, dividiendo los colores por 255 porque el atributo es de tipo gl.FLOAT y el shader espera valores de 0 a 1.

El código de comprobación no dibuja si el buffer no tiene datos para tres vértices. Si lo intentara con el buffer vacío del código de partida, WebGL no lanzaría ninguna excepción, pero gl.getError() devolvería INVALID_OPERATION (1282) y la consola mostraría GL_INVALID_OPERATION: glDrawArrays: Vertex buffer is not big enough for the draw call: WebGL comprueba que el buffer alcance para todos los vértices que pides, algo que OpenGL de escritorio no hace.

Un experimento que merece la pena: deja tu buffer correcto y pon STRIDE = 0. En WebGL, un stride de 0 no significa «sin avance», sino «datos compactos»: el stride pasa a ser el tamaño del propio atributo (8 bytes para la posición). Lo comprobé: gl.getError() dio 0 (no es un error) y la GPU leyó las posiciones (−0,8, −0,8), (1, 0) y (0, 0,8), es decir, x e y del primer vértice y después números que en realidad eran colores. Sale otro triángulo, con otros colores, y ningún aviso. Es el tipo de fallo que la lección 5.3 te enseñará a diagnosticar.

Ejercicio 1.6.4 — Tu propio formato binario

Diseña un formato para guardar nubes de puntos de colores en un ArrayBuffer: una cabecera con los 4 caracteres ASCII "PTS1" y el número de puntos (uint32, little-endian), y después, por punto, x e y en float32 little-endian y r, g, b en bytes, más 1 byte de relleno para que cada punto ocupe 12 bytes (y quede alineado). Escribe codificar(puntos) y decodificar(buffer) con DataView. La consola hace un viaje de ida y vuelta, compara, y muestra el volcado de la cabecera.

Pista 1

El punto i empieza en el byte 8 + i × 12. Dentro de él: x en +0, y en +4, r, g, b en +8, +9 y +10.

Pista 2

Un carácter ASCII es un byte: "P".charCodeAt(0) da 80. Para leerlo, String.fromCharCode(80).

Pista 3

No olvides el true final en setUint32, setFloat32 y sus lecturas. ¿Por qué no hace falta en setUint8?

Solución explicada

La cabecera ocupa 8 bytes: la firma "PTS1" (bytes 50 54 53 31 en hexadecimal) y el número de puntos como uint32 little-endian (con 2 puntos, 02 00 00 00). Cada punto ocupa 12 bytes: dos floats (8 bytes), tres bytes de color y uno de relleno. El relleno hace que cada punto empiece en un múltiplo de 4 (8, 20, 32…), así que los floats están alineados y otro programa podría leer las coordenadas con un Float32Array en lugar de DataView.

Todos los accesos de más de un byte llevan true para fijar el orden little-endian; los de un byte no lo necesitan (un byte no tiene orden). La comprobación compara x e y con Math.fround de los originales, porque al guardarlos como float32 pierden precisión: 0.1 vuelve como 0,10000000149011612. Por último, la firma sirve para rechazar datos que no son de este formato antes de interpretarlos: un archivo cualquiera leído como PTS1 daría números absurdos sin ningún error.

  • La GPU consume bytes. A gl.bufferData dale un TypedArray del tipo correcto: un array normal crea un buffer de 0 bytes sin ningún error, y un Float64Array da basura si el atributo es gl.FLOAT.
  • ArrayBuffer = bytes sin tipo; TypedArray = vista con tipo, longitud fija y conversión en cada escritura. Varias vistas pueden compartir un buffer: escribir por una cambia lo que ven las otras.
  • Una vista de N bytes por elemento debe empezar en un byteOffset múltiplo de N. DataView no tiene esa restricción.
  • La memoria es little-endian (1.0 en float32 son los bytes 00 00 80 3F). DataView usa big-endian por defecto: pasa siempre true.
  • Float32: signo, 8 bits de exponente, 23 de mantisa; ~7 cifras; enteros exactos hasta 16 777 216. Math.fround(x) te dice qué queda de x.
  • Uint8Array trunca y da la vuelta (300 → 44); Uint8ClampedArray redondea (medios al par) y satura (300 → 255).
  • subarray es una vista; slice, una copia; set copia en bloque. Transferir un buffer lo deja vacío en origen.
  • Vértices entrelazados: stride = bytes por vértice; offset = byte donde empieza cada atributo. Cuidado con mezclar índices de floats y bytes.
